# Sprout threat model

- **Status:** First draft (M0), updated after the M1 review and security audit (2026-11-02), the M2 review and security audit (2026-11-03), and the M3 review and security audit (2026-11-03). Reviewed at the end of each milestone and before release (M8).
- **Method:** STRIDE per asset and trust boundary.
- **Related:** [ADR-0002 Ledger as events](adr/0002-ledger-as-events.md), [ADR-0003 Security model](adr/0003-security-model.md), [ADR-0004 Parent authorisation and device identity](adr/0004-parent-authorisation-and-device-identity.md), [ADR-0005 Scheduled payments and money-flow atomicity](adr/0005-scheduled-payments-and-money-flow-atomicity.md), [ADR-0006 Sync protocol and document envelope](adr/0006-sync-protocol-and-document-envelope.md), [ADR-0007 Identity, linking and the device registry](adr/0007-identity-linking-and-device-registry.md), [privacy policy draft](PRIVACY.md), [incident runbook](RUNBOOK.md). Controls are mapped to SOC 2 criteria in [CONTROLS.md](CONTROLS.md).

## System overview

Each household has one or more parent devices and one or more kid devices. Every device keeps a local SQLCipher database and syncs through Firebase (Auth, Firestore; Storage from M4) under the security rules. Privileged operations (household creation, device registration and approval, link codes, revocation, export, deletion) run on the Sprout server, a Node service on Vercel that speaks the Firebase callable protocol with the Admin SDK (the project is on the Spark plan, which has no Cloud Functions; ADR-0007). App Check sits in front of the server, and of Firestore once enforced (M8). Ledger events are signed and hash-chained per author. Chat messages and chore photos are end-to-end encrypted between devices. All AI runs on device.

## Assets

| Asset | Description | Primary property |
|---|---|---|
| Kid identity data | First name, avatar, birth month and year, UI tier | Confidentiality, privacy |
| Chat content | Messages and voice notes between parent and kid | Confidentiality |
| Photos | Chore submission photos, often taken inside the home | Confidentiality |
| Ledger integrity | Event stream, balances, audit log | Integrity, non-repudiation |
| Parent credentials | Firebase session, passkeys and Google account link, parent PIN | Authentication |
| Device keys | Keystore P-256 device signing key and parent authentication key, Keystore PIN pepper key, X25519 agreement keys, thread keys, SQLCipher passphrase | Confidentiality, integrity |

## Actors

| Actor | Capability | Motive |
|---|---|---|
| Curious kid | Uses their own device and may borrow a parent's unlocked phone; no tooling | Peek at parent screens, award themselves credits |
| Malicious kid with a rooted device | Root, Frida, can edit local files, intercept app calls, change the clock | Inflate balance, bypass caps, approve own chores |
| Lost or stolen device | Physical access, possibly unlocked, possibly with a known screen lock | Read chat and photos, impersonate the household |
| Compromised Firebase project credentials | Admin SDK or console access (including the server's service-account key); bypasses security rules | Read or rewrite household data; receivers still refuse anything not signed by a registered device, but such an attacker can also rewrite the registry |
| Network attacker | On-path on public Wi-Fi; can block, delay, and replay traffic | Intercept or modify data in transit |
| Repackaged app | Modified APK or script using the real Firebase config | Scrape data, write forged documents, abuse the server's callables |
| Malicious insider at the platform | Access to storage or infrastructure at the cloud provider | Read stored data |

## Trust boundaries

| Boundary | What crosses it | Controls at the boundary |
|---|---|---|
| Device ↔ Firebase | Auth tokens, ledger events, documents, ciphertext | TLS, Firebase Auth, Firestore rules (membership, ACTIVE author device, role gates, conflict order, size bounds); App Check enforcement on Firestore from M8 |
| Device ↔ Sprout server | ID tokens, App Check tokens, callable requests with device proofs, attestation chains | TLS, ID-token verification with revocation check, App Check, device proofs, key attestation, rate limits, server-side validation |
| Sprout server ↔ Firebase | Admin SDK calls with a service-account key | Least-privilege service account, key held as a sensitive Vercel variable, ids-only logging |
| Parent device ↔ kid device (via Firebase) | Signed events, E2EE messages and photos, key material during linking | Device signatures, registered device list, X25519 + HKDF + AES-GCM, link codes |
| App ↔ OS keystore | Sign, decrypt, and unwrap operations; biometric prompts | Non-exportable Keystore keys (StrongBox where available), user-auth-bound parent keys, `CryptoObject` biometric |

Inside the app process, everything is trusted. A compromised OS on an unlocked device is out of scope (see below).

## Threats

STRIDE: **S**poofing, **T**ampering, **R**epudiation, **I**nformation disclosure, **D**enial of service, **E**levation of privilege.

| # | Threat | STRIDE | Asset | Mitigation | Status |
|---|---|---|---|---|---|
| T1 | Kid device submits a chore approval or reward as if from a parent | S, E | Ledger integrity | Custom claims set only by the server; rules take the role from `members/{uid}` and refuse PARENT-role events and every parent-only document from a KID member, and kid writes to decided submissions; receivers check the **registered** role of the author device, never `authorRole`, and quarantine parent-only events without a parent signature from a registered key of the authoring device covering the lamport (ADR-0004 M3 amendments, ADR-0007) | Mitigated M3 (rules, registry roles, receiver verification). Exemption: a household with `requireParentSignature = false` (no strong biometric, D-M2-1) accepts unsigned parent-only events from PARENT devices only (D-M3-32) |
| T2 | Replayed ledger event (re-sent by a rooted client or a network attacker) | T | Ledger integrity | Idempotency by `eventId` and content hash (same id and hash is a no-op); events create-only in the rules; per-author monotonic lamport and hash chain, so an out-of-sequence copy is held, never applied twice; a conflicting copy applies exactly one copy on every device (D-M3-30); TLS | Mitigated M3 (applied on pull and enforced by the rules) |
| T3 | Forged event carrying another author's `authorUid` or `authorDeviceId` | S, R | Ledger integrity | Rules require `authorUid == request.auth.uid` and an ACTIVE `authorDeviceId` of that uid; receivers verify the device signature against the registered key and check the uid and kid against the registry; signatures domain-separated; device keys attested at registration and unattested keys refused in production (D-M3-38); failures quarantined and shown in the "Rejected events" card | Mitigated M3. Gap: no real device attestation chain in the tests yet |
| T4 | Kid edits the local database on a rooted device to raise a balance | T, E | Ledger integrity | SQLCipher with a Keystore-wrapped passphrase; balances are projections, not stored truth; other devices recompute from signed events and verify every pulled event, so local edits never propagate; kid-authored credits limited to capped `GamePlayed` | Mitigated M3 (receivers verify and recompute) |
| T5 | Platform operator or holder of project credentials reads chat in the Firestore console | I | Chat content, photos | E2EE (ADR-0008): messages, voice notes and photos (chat and chore photos) are AES-256-GCM ciphertext under a per-(thread, epoch, creator) key; message plaintext is padded to a fixed bucket (presets, voice, photos) or 64-byte steps (text) before encryption; the AAD binds each ciphertext to its signed envelope or blob header, and a blob is opened only for the message or submission on screen (a chat blob: the message's thread, author device and photo hash; a chore photo: that submission's id and kid and its `photoRef.sha256`, never whichever submission names the blob id, audit A2-M1); thread keys travel only wrapped per member device (X25519 + HKDF) in PARENT-signed `thread_key` documents, one per creator; every encryption key is bound to its registered device by a device-key signature that the server and every receiver verify, small-order keys are refused, and receivers **pin** the keys and revocations they have seen (a changed key excludes the device; a revoked device never comes back; a row whose id is not its key's hash is dropped); private keys never leave the device (`SecretStore`, Keystore-wrapped); the server holds no keys; export carries envelopes and blob metadata only (D-M4-6) | Mitigated M4 (pinning, padding, blob binding: fix pass 2; chore photos bound to the submission on screen: fix pass 3). Decrypted plaintext never lands in a plain file: voice notes play from memory, recordings live in `cacheDir` only until encrypted, leftovers are swept at start-up (A2-M2). **T5 holds against a passive reader; the server is trusted for device admission (D-M4-16)**: a compromised server could admit a device of its own that parents then wrap new keys for (parent-confirmed admission is M7). No forward secrecy (D-M4-4): a device key extracted later opens every epoch ever wrapped for that device. Metadata stays visible (T37) |
| T6 | Linking code brute force | S, E | Kid identity data, ledger integrity | 8 characters (40 bits) from a CSPRNG, 10-minute TTL, single use, at most 5 live per household; stored as `HMAC-SHA256(LINK_CODE_HMAC_KEY, code)`; rate limits counted before the lookup (10 / hour per uid and per IP, 20 / hour per code id); wrong, used and expired codes answer alike; creating a code needs a parent device proof; App Check on the callable; never in URLs or logs | Mitigated M3. Relies on the server environment (`LINK_CODE_HMAC_KEY`, TTL policies) |
| T7 | Stolen parent phone, or a kid holding an unlocked parent phone or knowing the screen lock | S, I, E | Parent credentials, all assets | Parent area behind PIN or biometric with exponential lockout (served time kept across reboots; biometric re-auth after the cap, or one attempt per hour while no usable biometric exists) and auto-lock on background; PIN hashed with Argon2id (PBKDF2 fallback) over input peppered by a non-exportable Keystore HMAC key; parent key created and renewed only in PIN-gated flows and needs a strong biometric per signature; privileged callables need a device proof from an ACTIVE parent device; `FLAG_SECURE`; **remote revocation** from another parent device: the device's later writes are refused everywhere and the parent's sessions are revoked (`tokensValidAfter`). The revoked phone can no longer refresh its sign-in, so it does not rely on a sync: the next time it starts (or a sync is refused) with a network, it is gated behind "Sign in again" (no household data shown) and asks the server about itself with the token-less, device-signed `deviceStatus` (D-M3-48); REVOKED or a deleted household erases its copy (one durable wipe owner, also from a background worker, resumed after a process death; D-M3-47). A phone that never comes online again keeps its encrypted (SQLCipher, Keystore-wrapped key) copy behind the gate and the PIN. Erasing it from the gate instead shows the unsynced changes that would be lost and needs the parent PIN when the phone has one; a sign-in on the gate with another account is signed out again before any sync runs. Signing out erases the phone's copy | Mitigated M3 (revocation, session revocation, device proofs, wipe on next launch with network); M4 chat key rotation on revocation (T17). Reads after a re-sign-in: T33. A household with one parent device cannot revoke it (RUNBOOK §2) |
| T8 | Kid device (or an attacker's device) added to the household without approval | S, E | All household data | Kid linking needs a code created by a parent device (device proof); a second parent device is PENDING until an ACTIVE parent device approves it after a fingerprint comparison, with a signed approval; the rules refuse PENDING devices' writes and receivers hold what they wrote; every device listed in Settings → Devices with its attestation level | Mitigated M3. Reads by a PENDING device: T33 |
| T9 | PII in crash logs or analytics | I | Kid identity data, chat content | No analytics SDKs; Crashlytics opt-in with PII scrubbing; Timber release tree drops below WARN; lint forbids `android.util.Log` and logging model types; no chat plaintext or names in logs | Partial M0 (Detekt bans `android.util.Log`). The app still has no logging call sites, so no Timber tree is planted yet. M3: the server logs ids and counts only through one entry point (`server/src/log.ts`, ESLint, `logging.test.ts`). Crashlytics not added; decision M8 |
| T10 | Compromised dependency or build plugin | T, E | All | Gradle dependency verification with SHA-256 checksums only (no PGP signature verification; trust on first use), refreshed by a workflow on Renovate branches; Renovate with reviewed, grouped PRs; OWASP Dependency-Check in a weekly and manual workflow; Actions pinned by SHA; branch protection; secret scanning | Done M0 (checksums, Renovate, Dependency-Check workflow, SHA-pinned Actions); secret scanning and branch protection are repo settings, enable in repo settings |
| T11 | Repackaged app or script calling Firebase with the real config | S, E, D | All household data | App Check: Play Integrity provider in release; the server requires and verifies an App Check token on every callable; rules still apply to anything that reaches Firestore; device proofs and attested registration make a script without a registered device key useless for privileged calls; rate limits | Partial M3: callables gated; **Firestore App Check enforcement is a console step (M8)**, so until then a script with a valid member session reaches Firestore under the rules; Play Integrity not yet exercised against the real project |
| T12 | Kid changes the device clock to game daily caps or allowance timing | T | Ledger integrity | Ordering by lamport, not `createdAt`; daily cap per kid, date and currency, over-cap events rejected rather than clamped; every Firestore write carries a server-stamped `serverReceivedAt`; allowance driven by parent devices | Partial M3 (server timestamp stored with every write; the cap date is not yet checked against it, M5) |
| T13 | Network attacker intercepts or modifies traffic | I, T | All in transit | TLS via the Firebase SDKs and to the server (HTTPS, Vercel); Network Security Config forbids cleartext (debug builds allow it to the emulator hosts only); signatures on events, documents and privileged calls detect modification independently of TLS; AEAD for chat and photos | Mitigated M3 (TLS, signed documents and calls); M4 (signed, AEAD-encrypted messages and blobs, ADR-0008) |
| T14 | Backup or device transfer extracts the database or keys | I | Device keys, local data | `allowBackup=false`; data extraction rules exclude every domain from cloud backup and device transfer; Keystore keys are non-exportable; wrapped secrets live in `noBackupFilesDir` | Done M0 (backup exclusions); M1 (Keystore-wrapped secrets in `noBackupFilesDir`) |
| T15 | Screenshot, screen recording, or task switcher leaks parent or chat screens | I | Chat content, kid identity data | `FLAG_SECURE` on parent and chat screens (`SecureWindow` on the chat inbox and both thread screens, kid mode included, M4); lint check for missing flag on sensitive screens | Partial M4 (parent area and chat screens); lint check and audit M7 |
| T16 | Parent denies having made a manual adjustment | R | Ledger integrity | Every parent-only event carries a `parentSignature` from the biometric-bound parent key, verified by every receiver against a registered key of the authoring device (server-registered, attested TEE/StrongBox with biometric per use); append-only audit log with author, device and time | Mitigated M3. Gap: the app sends no attestation chain for the parent key yet, so production refuses its registration (CONTROLS IA-19). Households without a strong biometric (D-M2-1) have no parent signature to point to |
| T17 | Removed device keeps reading new chat messages | I | Chat content | On a revocation the next PARENT device to sync creates epoch + 1 wrapped for the remaining members only (`ThreadKeyMaintenance`, run at start-up and after every sync under one lock; D-M4-7); the check covers the union of every creator's document of the latest epoch, so a concurrent rotation by another parent cannot keep the device in; a device dropped by a later epoch is never wrapped again by a re-wrap from a lagging registry mirror; a device whose registered encryption key changed is treated like a removed one; senders never use an epoch whose wrap sets hold such a device, never send under their own key before the server confirmed its document, and wait for a parent device instead; the revoked device's sessions and kid account are revoked and the rules refuse its reads and writes; it wipes its copy on its next launch with a network (ADR-0007): database, blob cache, secrets and the whole `cacheDir`, so no decrypted voice clip or recording survives (audit A2-M2; decrypted clips are never written to files in the first place) | Mitigated M4 (fix pass 2: per-creator documents, union check, confirmation). What the device already held (earlier epochs, in its encrypted database) stays readable on it until that wipe; rotation waits for a parent device to come online |
| T18 | Flooding the outbox or the server to exhaust quotas | D | Availability | Per-uid, per-IP and per-code rate limits on every callable (right-most `X-Forwarded-For` hop, T34); App Check on the callables; closed key sets and string bounds on every Firestore write; callable bodies at most 256 KB; export at most 4 MB (T35); held rows capped at 500 per author device (events, documents, messages); at most 60 new blob chunks per household per UTC day (`quotas/{yyyymmdd}`, D-M4-18); on the device, outbox rows are read without their chunk bytes and a push batch carries at most two 700 KB chunks; a gap held for a day is skipped; implausible thread key epochs (more than 1,000 above the known ones) are ignored | Partial M3, M4. Budget alerts and Firestore App Check enforcement M8 |
| T19 | Ledger overflow or poison event: an event with a huge amount makes `Money` arithmetic overflow and the projection throw, so no balance in the household can be shown | D, T | Ledger integrity, availability | Every amount bounded by `maxAmount` (10^12 minor units) as a static rule; projection handles each event on its own, turning an overflowing or invalid event into an `InvalidEvent` anomaly and carrying on; projection never throws on event content (ADR-0002 amendments) | Done M1 |
| T20 | Lamport exhaustion: a forged or corrupt remote event with a lamport near `Long.MAX_VALUE` drags every device's clock up until ordering breaks | D, T | Ledger integrity | Remote events whose lamport exceeds the local maximum by more than `maxLamportJump` (1,000,000) are quarantined, remote documents above it held; `LamportClock.observe` ignores such jumps (ADR-0004 §4) | Mitigated M3 |
| T21 | Unbounded free text in events leaving the device: adjustment reasons and compensation notes can hold personal data and are plaintext to the backend (the ledger is signed, not encrypted) | I | Kid identity data | Free-text fields bounded to 200 characters; redacted in `toString`, so they cannot reach logs or crash reports; listed as collected data in [PRIVACY.md](PRIVACY.md). The chore submit sheet's draft (chore id and title, the kid's note of at most 200 characters, the pending photo's file name and a SHA-256 of its plaintext) is kept in the activity `SavedStateHandle` while the app is backgrounded; it is excluded from backup (`allowBackup=false`, T14), never logged (T9), and the photo bytes never enter the `Bundle` | Done M1 (bound, redaction); disclosure finalised M8 |
| T22 | Demo seed data in release builds: the bootstrap that seeds a sample household ships to users, mixing fake kids and events into real ledgers | T, I | Ledger integrity, kid identity data | Bootstrap gated to debug builds; release builds start empty | Done M1 |
| T23 | Wrapped secret blob missing while the database exists (file deleted, partial restore, storage corruption) | D | Local data, availability | `SecretStore` never regenerates a secret it cannot unwrap or find, so a fresh passphrase is never silently paired with an old database; opening the database fails instead. Recovery is `WipeLocalDataUseCase` and re-pulling from the household after signing in again | Partial M3: the wipe and re-pull exist (run on household gone); no automatic recovery path from an unopenable database yet |
| T24 | Lazy parent-key creation: a kid who knows the parent's screen lock enrols their own fingerprint, and the app creates the parent key on first use, so the kid can sign parent-only events without ever knowing the parent PIN | S, E | Ledger integrity, parent credentials | Parent key created only in a PIN-gated enrolment flow (at PIN setup, or from Settings with a fresh PIN); biometric unlock and per-event authorisation offered only when the local key byte-equals the key registered in the household policy (ADR-0004 amendments) | Mitigated M2 (this PR) |
| T25 | Fingerprint-change recovery: after a biometric enrolment change invalidates the parent key, a recovery path that recreates the key without the PIN hands the key to whoever enrolled the new fingerprint, or a missing path locks the parent out | S, E, D | Parent credentials, ledger integrity | Renewal is PIN-gated (fresh PIN under the lockout policy, delete, create, proof prompt, replace the registered key keeping the original from-lamport); while no usable key or strong biometric exists the lockout cap allows one PIN attempt per hour instead of closing (ADR-0004 amendments) | Mitigated M2 (this PR) |
| T26 | Unverified parent signature before registration: an event signed by whatever key sits under the parent alias is accepted as parent-signed, and the biometric unlock challenge is checked against that same unregistered key | S, E | Ledger integrity | Signatures and the unlock challenge verified against the registered parent key only; receivers accept only keys the server registered, bound to the authoring device and fingerprint-checked; a signature by any other key counts as unsigned | Mitigated M3 |
| T27 | Unsigned reward catalogue: a rooted kid device edits a reward's cost or minutes, buys it cheaply or for extra minutes, and receivers cannot tell the purchase from a legitimate one | T, E | Ledger integrity | Rewards are device-signed documents (`sprout/document/v1`) that only a PARENT device may write (rules and receivers); the catalogue accepts only rewards whose stored envelope verified against a PARENT device key and re-verifies them from the stored row (D-M3-3, D-M3-27) | Mitigated M3 |
| T28 | Prompt without disclosure: a biometric prompt that does not say what it signs lets a parent approve a payment they did not intend (or a run of prompts at unlock trains them to approve blindly) | R, E | Ledger integrity | Every parent-signature prompt names the kid, the amount, and the period or chore; scheduled payments signed only from a manual "Sign now", never automatically at unlock (ADR-0004 amendments, ADR-0005) | Mitigated M2 (this PR) |
| T29 | Camera cache leftovers: plaintext chore photos stay in the camera cache after the encrypted copy is written | I | Photos | Camera cache cleared before each capture and at app start (ADR-0005) | Mitigated M2 (this PR) |
| T30 | Photo retention: encrypted chore photos accumulate on the device after the submission no longer needs them | I | Photos | Encrypted photo deleted when its submission is decided and when the chore or kid is archived (ADR-0005) | Mitigated M2 (this PR) |
| T31 | Ledger overflow from queued actions: a scheduled allowance or interest action that breaks ledger rules (amount over `maxAmount`, overflow) is prompted for, refused after signing, and re-prompted on every drain | D, T | Ledger integrity, availability | Pending actions validated against the ledger rules before any prompt; invalid ones marked `FAILED` and never re-prompted; actions from a changed schedule cancelled and re-planned; draining serialised (ADR-0005) | Mitigated M2 (this PR) |
| T32 | Equivocation: a cloned or rooted device signs two different histories (two events on one `prevHash`), showing each branch to different devices so they disagree | T, R | Ledger integrity | Fork detection on ingest: every branch is quarantined `FORKED_CHAIN` on every device, including a branch already applied, with its stored descendants, and projections are rebuilt; rows the verifier refused never count as branches, so a forgery cannot kill a real chain (ADR-0006 §6, D-M3-31, D-M3-36) | Mitigated M3 |
| T33 | Reads without an active device: any signed-in session of a member uid reads the household, including a PENDING second phone of the parent's account and a stolen phone signed back in with the parent's Google account after its device was revoked | I | Kid identity data, ledger | Writes need an ACTIVE device (rules); revocation revokes the account's sessions, so a re-sign-in is needed; RUNBOOK §2 has the parent secure the Google account; App Check enforcement on Firestore (M8) limits reads to the genuine app | Accepted risk until M8 (see accepted risks) |
| T34 | `X-Forwarded-For` spoofing: a client prepends hops so the server keys per-IP limits on an address it chose, escaping the limit or exhausting another client's bucket | S, D | Availability, link codes | The server uses the **right-most** hop (the one Vercel's edge adds); IPv6 keyed per /64; requests without a usable address share one stricter bucket; per-uid and per-code limits apply regardless | Mitigated M3. Breaks if a further proxy is put in front without configuring the hop count (FIREBASE.md) |
| T35 | Export size DoS: a large household makes `exportHousehold` build a response that exhausts the server's memory or exceeds the host's 4.5 MB response cap | D | Availability | Export refused with `resource-exhausted` above 4 MB (D-M3-35); 5 exports / hour per uid, 10 per IP; device proof required | Mitigated M3. Large households cannot export until a signed-URL export exists |
| T36 | Trial-data leak or loss at linking: data from the pre-sync trial household (signed by an unregistered key) is uploaded into the real household, or deleted without the parent knowing | T, I | Ledger integrity, kid identity data | Trial data is never uploaded; an explicit confirmation screen precedes `PurgeLocalHouseholdUseCase`, which deletes the trial household's rows, photos and policy in one transaction and records one audit row (ADR-0007 §9) | Mitigated M3 |
| T37 | Chat metadata visible to the backend: who wrote in which thread, when, how much, and which devices hold a thread key | I | Chat routing data, kid identity data | Content is encrypted (T5); the thread id is the kid id, so the metadata reveals no more than the registry already holds. Visible: household, thread, author uid, device and role, `seq`, lamport, `createdAt` and receive times, kind, epoch, the padded ciphertext size (one bucket for presets, voice notes and photos; 64-byte steps for text), blob ids, chunk counts and sizes (photos downscaled, voice ≤ 30 s), each thread key document's creator and recipient devices, and the registry; message text never reaches logs (T9). Padding added in M4 fix pass 2 |

## Accepted risks

| Risk | Rationale |
|---|---|
| **Time bank runs on the honour system.** A kid can start the time bank and keep using the device after it runs out, or never start it. | Enforcement needs Accessibility, UsageStats, overlay, or device-admin permissions, which bring Play policy review and a much larger attack surface. v1 records time spent; it does not enforce it. The ledger still records every purchase and start/stop accurately. |
| **E2EE chat history is lost if every household device is lost.** | Keys exist only on devices. Server-side key escrow would undermine the E2EE claim, and recovery phrases are a lockout risk for families. Chat is not the system of record for anything; the ledger is plaintext-signed and recoverable after re-authentication. Parents are told this at chat setup. |
| Backend can see chat metadata (who, when, size; T37). | Needed for routing, ordering and notifications. Content stays encrypted (ADR-0008). |
| ~~M1 only: parent-only events are authorised by a self-declared role~~ (T1, T16). | **Closed in M3**: receivers check the registered role and verify parent signatures; trial-household events are purged at linking, never uploaded (ADR-0004 M3 amendments, ADR-0007 §9). |
| **Hourly PIN attempts after the lockout cap** while the parent key is invalidated or the device has no strong biometric (T7, T25). | Closing the PIN path for good would lock the parent out of their own household. One attempt per hour gives an attacker holding the device about 24 guesses a day against 10^6 six-digit PINs, and the Keystore pepper keeps the search on that device (ADR-0004 amendments, D-M2-7). |
| **Reads gated by membership, not by device** (T33): a PENDING phone of the parent's account, or a stolen phone signed back in with the parent's Google account, can read the household. | Writes need an ACTIVE device, so nothing can be changed. Gating reads on a device would need every read to carry a device proof, which the Firestore SDK cannot do. App Check enforcement on Firestore (M8) removes scripted access; securing the Google account (RUNBOOK §2) removes the re-sign-in. |
| **Parent-signature exemption for households without a strong biometric** (T1, T16; D-M2-1, D-M3-32). | Kept by Kiril on 2026-11-03 so such families can use money features. Only PARENT devices benefit, the household policy that grants it is parent-written and synced, and Settings shows a warning. |
| **Attestation leniency in the details** (T3, T8): a `SOFTWARE`-attested device key is accepted; the verified boot state is logged, not enforced; if Google's revocation list cannot be fetched, the chain is accepted with a warning. | Unattested keys are refused in production; a software keystore is still evidence of where the key lives and is shown in Settings. Enforcing boot state would exclude custom-ROM users; failing closed on a Google outage would block every registration. Parent keys must be TEE or StrongBox. |
| **No server-side backups** (Spark plan). | Firestore's own durability only; scheduled backups and point-in-time recovery need the Blaze plan. Revisit at M8 (CONTROLS AV-7). |
| **A household with a single parent device cannot recover from losing it in the app** (T7). | Only an ACTIVE parent device can approve or revoke. The operator path is documented in RUNBOOK §2 and needs a script that does not exist yet; parents are encouraged to approve a second device. |
| **Rate-limit buckets hash IP addresses without a salt.** | An IPv4 bucket id is reversible by enumerating 2^32 addresses; rows hold no other data and expire with their window (at most one hour plus the TTL sweep). |

## Out of scope for v1

- **Device enforcement** of screen time (blocking apps, locking the device). If it is ever built, it goes in an isolated module behind a feature flag with its own policy review and threat model.
- **OS-level compromise of an unlocked parent device** (malware with root or Accessibility on the parent's phone while unlocked). Such an attacker can drive the UI. Parent-only events still need a strong biometric per signature (ADR-0004), but the attacker can raise the prompt at a moment the parent does not expect. Mitigations stop at Keystore non-exportability, per-use biometric binding, and auto-lock.
