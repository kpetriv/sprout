# M3 — Sync and identity

Scope from `docs/PLAN.md` M3 plus the M3 items of ADR-0004 (device registry, attestation, parent-key registry, purge of local-household data, no from-lamport exemption on pull, role-verified parent-wins) and ADR-0005 (signed reward catalogue). Implemented on branch `m3/sync-identity`; lands as one PR. Decisions taken with a default are logged as D-M3-x in `docs/DECISIONS-PENDING.md`.

There is no real Firebase project yet. Everything is built and verified against the **Firebase Emulator Suite** (Auth, Firestore, Functions); the production wiring (Play Integrity App Check, Google sign-in through Credential Manager, `google-services.json`) is implemented but can only be exercised once a project exists (D-M3-1).

## Target architecture

```
core/sync            JVM. Ports + SyncEngine + DocumentEnvelope + ConflictResolver + FakeSyncTransport (testFixtures)
core/domain-ledger   + DeviceRegistry port, RemoteEventVerifier, IngestOrdering, role-verified appliedCopyOf
core/database        implements the ports: outbox source, remote applier, registry, ledger ingest, session store, purge
core/sync-firebase   FirebaseSyncTransport, FirebaseAuthSession, HouseholdFunctions client, App Check install
feature/onboarding   sign-in, create household, link this device (kid), register + approve a second parent device
feature/settings     + Devices (list, approve, revoke), sign out, export, delete household
app                  SyncWorker + foreground listener, role-driven mode, purge flow, Firebase bootstrap
functions/           TypeScript Cloud Functions + tests
firestore/           rules + rules tests, emulator config
```

Dependency direction: `core/database → core/sync → core/domain-ledger → core/model`. `core/sync-firebase → core/sync`. Only `core/sync-firebase` imports Firebase SDKs (ADR-0001).

## 1. Identity model

- **Users.** A parent is a Firebase Auth user signed in with Google through Credential Manager (release) or with email/password against the Auth emulator in debug builds (D-M3-2). A kid device is an **anonymous** Firebase Auth user. Custom claims set by Cloud Functions only: `{ hid: HouseholdId, role: "PARENT" | "KID", kidId?: KidId }`. A uid belongs to at most one household (v1).
- **Devices.** Every device has one P-256 Keystore key (`sprout.device.signing.v1`, existing `DeviceKeyStore`). `DeviceId` stays the hex SHA-256 fingerprint of the SPKI. At registration the device generates a **fresh** key with `setAttestationChallenge(challenge)` where the challenge comes from the function (`beginDeviceRegistration`), under a new alias `sprout.device.signing.v2`; the v1 key is deleted after the v2 key is registered. The attestation chain is sent to the function, which verifies it (Google root, challenge match, key origin, security level) and records `attestation: STRONGBOX | TEE | SOFTWARE | NONE`. In the emulator project unattested keys are accepted and recorded as `NONE` with a visible "unverified device" label in Settings (D-M3-5). The function never accepts a device whose attested public key differs from the submitted one.
- **Registry documents** (Firestore, under `households/{hid}`):
  - `devices/{deviceId}`: `{ uid, role, kidId?, publicKey (base64 SPKI), attestation, status: PENDING | ACTIVE | REVOKED, registeredAt, approvedBy?, revokedAt?, lamport }`. Written by functions only.
  - `parentKeys/{fingerprint}`: `{ publicKey, uid, deviceId, validFromLamport, revokedAtLamport?, registeredAt }`. Written by a parent device (rules: role PARENT, `deviceId` is an ACTIVE device of `request.auth.uid`), never updated except to set `revokedAtLamport` (by functions on device revocation). This replaces the single `household_policy.parentPublicKey` for verification: a parent signature is valid when it verifies against a key whose `validFromLamport <= event.lamport` and (`revokedAtLamport == null || event.lamport < revokedAtLamport`).
  - `members/{uid}`: `{ role, kidId?, addedAt }`. Functions only. Mirrors the claims so rules can `get()` the role without trusting client data.
- **Flows** (all callable functions, App Check required outside the emulator, per-uid and per-IP rate limits, T6/T18):
  - `createHousehold({ fiatCurrency, devicePublicKey, attestationChain? })` → creates `households/{hid}`, `members/{uid}` PARENT, `devices/{deviceId}` ACTIVE, sets claims. Returns `{ hid }`.
  - `beginDeviceRegistration()` → `{ challenge }` (32 random bytes, base64, 10-minute TTL, stored hashed under `challenges/{uid}`).
  - `registerParentDevice({ devicePublicKey, attestationChain? })` → for a uid that already has PARENT claims (same Google account on a second phone): creates `devices/{deviceId}` **PENDING**. Returns `{ deviceId, fingerprint }`. The existing parent device shows the fingerprint; `approveDevice({ deviceId })` (caller must be an ACTIVE PARENT device, checked by the caller's `deviceId` argument + signature over `"sprout/approve-device/v1" || deviceId` with its registered key) flips it to ACTIVE. T8.
  - `createLinkCode({ kidId })` → 8 characters from `ABCDEFGHJKLMNPQRSTUVWXYZ23456789` (no 0/O/1/I), crypto-random, 10-minute TTL, single use, stored as `linkCodes/{sha256(code)}` with `{ hid, kidId, createdBy, expiresAt, used: false }`. Max 5 live codes per household; 10 attempts per IP per hour. Never logged. T6.
  - `redeemLinkCode({ code, devicePublicKey, attestationChain? })` → caller is an anonymous user; validates the code, marks it used, creates `members/{uid}` KID, `devices/{deviceId}` ACTIVE, sets claims `{ hid, role: KID, kidId }`. The kid device then forces a token refresh.
  - `revokeDevice({ deviceId })` → PARENT only; sets `status: REVOKED`, `revokedAt`, and `revokedAtLamport = latest lamport seen for that device + 1` on every `parentKeys` row with that `deviceId`. A revoked kid device's anonymous user is disabled. T7.
  - `exportHousehold()` → PARENT only; returns a JSON bundle (households doc, members, devices, parentKeys, every document collection, every event) inline (callable limit 10 MB; D-M3-7). The device writes it to a file the parent shares (SAF `ACTION_CREATE_DOCUMENT`) and derives a ledger CSV from it.
  - `deleteHousehold({ confirmation: hid })` → PARENT only; recursive delete of `households/{hid}`, deletes every member's Auth user (anonymous kids and the parents), writes `deletionRecords/{autoId}` `{ hidHash: sha256(hid), at, counts }` and nothing else (PRIVACY.md). Devices that next sync and find the household gone (or get `permission-denied` with no household claim) wipe local data (§6).
- **Session on device** (`core/database` `SessionStore`, encrypted via `SecretStore`): `{ uid, hid, role, kidId?, deviceId, deviceStatus, signedInAt }`. `SessionAuthorProvider` reads it; `LocalOnlyAuthorProvider` is deleted. `EventAuthor.householdId/uid/role/deviceId` come from the session. A KID session cannot produce a PARENT author (`kidAuthor` is removed; kid mode on a parent device still signs as the parent device with role KID? **No**: on a parent device, kid mode writes are authored by the parent uid with `role = KID` and `onBehalfOfKid = kidId`? Keep it simple and honest: on a parent device, kid-mode purchases are authored `role = KID, uid = parent uid, deviceId = parent device`; the registry role of the device is PARENT, so receivers accept KID-role events from a PARENT device (a parent may act as any role) but never PARENT-role events from a KID device.)

## 2. Ledger ingest (core/domain-ledger + core/database)

Pure Kotlin in `core/domain-ledger`:

```kotlin
interface DeviceRegistry {
    suspend fun device(deviceId: DeviceId): RegisteredDevice?
    suspend fun parentKeys(): List<RegisteredParentKey>
}
data class RegisteredDevice(val deviceId: DeviceId, val uid: UserId, val role: Role, val kidId: KidId?,
    val publicKey: ByteArray /* SPKI DER */, val status: DeviceStatus, val attestation: AttestationLevel)
data class RegisteredParentKey(val fingerprint: String, val publicKey: ByteArray, val validFromLamport: Long, val revokedAtLamport: Long?)
fun interface SignatureCheck { fun verify(publicKey: ByteArray, payload: ByteArray, signature: ByteArray): Boolean }

class RemoteEventVerifier(registry: DeviceRegistry, check: SignatureCheck, policy: LedgerPolicy) {
    suspend fun verify(json: JsonObject, localMaxLamport: Long): VerifiedRemote
}
sealed interface VerifiedRemote { data class Ok(val event: LedgerEvent, val json: JsonObject) ; data class Quarantined(val eventId: EventId?, val hash: String?, val reason: QuarantineReason) }
enum class QuarantineReason { UNDECODABLE, HASH_MISMATCH, UNKNOWN_DEVICE, DEVICE_NOT_ACTIVE, UID_MISMATCH, ROLE_NOT_ALLOWED, BAD_DEVICE_SIGNATURE, PARENT_SIGNATURE_MISSING, PARENT_SIGNATURE_INVALID, LAMPORT_TOO_FAR_AHEAD, SCHEMA_UNSUPPORTED }
```

Checks, in order: decode (`LedgerJson.decodeOrNull`, schema 1 or 2), hash over the stored tree, device registered and ACTIVE (REVOKED devices: events with `lamport < revokedAtLamport` of that device are still accepted, later ones quarantined `DEVICE_NOT_ACTIVE`), `authorUid == device.uid`, role allowed (`PARENT` role requires `device.role == PARENT`), device signature, parent signature when `event.isParentOnly()` **regardless of lamport** (no from-lamport exemption, ADR-0004 amendment) against `parentKeys()` valid at `event.lamport`, `lamport <= localMaxLamport + policy.maxLamportJump`. Any failure is a `Quarantined` with the first failing reason.

`IngestOrdering.plan(batch: List<VerifiedRemote.Ok>, heads: (DeviceId) -> Pair<String?, Long>): IngestPlan` groups by author, sorts by lamport, walks each stream from the stored head and returns `apply: List<LedgerEvent>` (chain-linked, in order) and `held: List<LedgerEvent>` (gap before them: `prevHash` does not match the running head). Held events go to `ledger_inbox` and are retried on the next ingest.

`appliedCopyOf(copies, registry)`: the role of a copy is `registry.device(copy.authorDeviceId)?.role`, not the envelope's `authorRole`; a parent copy wins only when its parent signature verified (the verifier marks `LedgerEvent` copies it accepted; conflicting copies are re-verified at projection time through the stored `quarantined = false` flag). The old self-declared overload is deleted; `Ledger.project` takes a `roleOf: (DeviceId) -> Role?` (default: envelope role, for the in-memory fixtures).

`LedgerRules.validate` stays as is; `UnknownAccount` is avoided by ingest order (§4).

`core/database`:
- `RoomLedgerRepository.ingest(jsons: List<JsonObject>): IngestResult(applied, duplicates, quarantined, held)`, one transaction per batch: verify → plan → for each applicable event `LedgerRules.validate` against the projection before it → store with `EventOrigin.REMOTE`, no outbox row, audit `LEDGER_EVENT_INGESTED`; invalid ones stored `quarantined = true` + `quarantineReason` (+ audit `LEDGER_EVENT_QUARANTINED` with reason and ids only); conflicting copies stored as evidence (`LEDGER_EVENT_CONFLICT`). The device clock observes the max applied lamport (`advanceDeviceLamport`). `signatureFailure` on read now verifies REMOTE rows against the registry (fallback: keep quarantine as stored when the device is unknown).
- Tables (schema v3, `MIGRATION_2_3`, migration test): `devices`, `parent_keys`, `ledger_inbox(eventId, hash, payloadJson, authorDeviceId, lamport, receivedAtEpochMs)`, `sync_cursor(collection PK, cursor)`, `session(id=0, …)`; `authorUid`, `authorDeviceId` and `signature` columns on every document entity; `kids` and `accounts` get `lamport`, `authorUid`, `authorDeviceId`, `signature`.
- `RoomDeviceRegistry : DeviceRegistry` over `devices` + `parent_keys` (both synced read-only from Firestore).
- `household_policy.parentPublicKey` stays as "this device's registered parent key" for the lock UI; `HouseholdPolicySource` verification switches to the registry (`ActivePolicy.parentKeys`). `registerParentKey` also enqueues a `parent_key` document (outbox) so other devices learn it; `parentSignatureFromLamport` is no longer consulted on ingest.
- A quarantined-event reader: `observeQuarantined(): Flow<List<QuarantinedEvent>>` for the parent audit card (`feature/parent-home` "Rejected events" card: count + reason + device label; no payload shown).

## 3. Documents, envelope and conflicts (core/sync)

```kotlin
@Serializable data class DocumentEnvelope(val schemaVersion: Int = 1, val householdId: HouseholdId, val docType: String, val docId: String,
    val authorUid: UserId, val authorDeviceId: DeviceId, val lamport: Long, val deleted: Boolean = false,
    val payload: JsonObject, val signature: String /* base64 ECDSA over "sprout/document/v1" || 0x00 || canonical(envelope minus signature) */)
```

- Every document write (`DocumentWrites.record`) builds an envelope, signs it with the device key, and stores the envelope JSON in `outbox.payload`. Kids, accounts, the household policy (fiat currency + `requireParentSignature`) and parent keys become documents: `docType` ∈ `kid, account, household_policy, parent_key, chore, chore_submission, reward, allowance_schedule, savings_goal, interest_policy`. Receivers verify the signature against the registry and the **role**: `chore, reward, allowance_schedule, savings_goal, interest_policy, kid, account, household_policy, parent_key` need a PARENT device; `chore_submission` from a KID device must have `kidId == device.kidId` and status `SUBMITTED`. This is how the reward catalogue becomes parent-signed (ADR-0004 amendment, T27; D-M3-3): `PurchaseCatalogue` accepts only rewards whose stored envelope verified against a PARENT device key.
- `ConflictResolver.resolve(local: Stored?, remote: DocumentEnvelope): Decision` = `Apply | Ignore`: LWW on `(lamport, authorDeviceId.value)`; `chore_submission` uses `SubmissionStatusPrecedence.merge` on the payloads first (status precedence beats lamport); tombstones (`deleted = true`) win over any lower lamport and are kept as rows with `deleted = true` (new column) so a late update cannot resurrect them.
- Remote document lamports are observed by the device clock (`LamportClock.observe` semantics, bounded by `maxLamportJump`; above the bound the document is quarantined to `document_inbox` with a reason, same audit as events).
- Account ids are deterministic: `AccountId("${kidId}.${currency}.${kind}")` for new households (D-M3-4). Submission ids already are.
- `ChoreSubmission.photoRef` stays in the payload; receivers keep it but `PhotoStore.load` of an unknown file returns null and the approvals UI shows "photo on the kid's device" (D-M3-9, M4 uploads it).

## 4. Sync engine (core/sync)

```kotlin
interface SyncTransport {
    suspend fun push(events: List<JsonObject>, documents: List<DocumentEnvelope>): PushResult   // per-item ack/reject, idempotent
    suspend fun pull(cursor: SyncCursor): PullPage                                               // registry + documents + events since cursor
    fun changes(): Flow<RemoteChange>                                                            // live listener while foregrounded
    suspend fun isAvailable(): Boolean
}
interface OutboxSource { suspend fun due(limit: Int): List<OutboxItem>; suspend fun ack(seq: Long); suspend fun fail(seq: Long, error: SyncError, nextAttemptAt: Long) }
interface RemoteApplier { suspend fun applyRegistry(devices, parentKeys, members); suspend fun applyDocuments(List<DocumentEnvelope>): ApplyReport; suspend fun applyEvents(List<JsonObject>): IngestResult; suspend fun cursor(): SyncCursor; suspend fun saveCursor(SyncCursor) }
class SyncEngine(transport, outbox, applier, clock, backoff = Exponential(1s..1h, jitter)) { suspend fun syncOnce(): SyncReport; fun run(scope): Job }
```

- Order of a `syncOnce`: pull registry → pull documents (apply order `kid, account, household_policy, parent_key`, then the rest) → pull events (ingest) → retry `ledger_inbox` → push outbox in `seq` order (stop at first transient failure; permanent rejections are acked with an audit row `SYNC_REJECTED` and surfaced in the parent audit card). Pull before push so `UnknownAccount` cannot happen for remote accounts. Idempotent: pushing an already-present event or an equal-or-lower-lamport document is a success.
- `SyncError`: `Transient(retryAfter)` | `Permanent(code)` | `Unauthenticated` | `HouseholdGone`. `HouseholdGone` triggers the wipe (§6). `lastError` on the outbox row stores the code only.
- `FakeSyncTransport` (testFixtures): an in-memory "server" shared by N transports, with `partition(deviceId)`/`heal()`, server-side rule emulation for the role gates and immutability, and Firestore-like LWW on push. Engine tests: two devices, interleaved offline writes converge (balances equal, same document state), a forged event (bad signature, wrong author, revoked device, parent-only without parent signature) is quarantined on the receiver and never applied, held events apply once the gap is filled, document LWW and submission precedence converge regardless of order, a tombstone is not resurrected, lamport jump above the bound is quarantined.
- `core/database` convergence test (Robolectric): two `TestHousehold`s (moved to `core/database` testFixtures; `testFixtures { enable = true }`) with distinct software device keys, a shared `FakeSyncTransport`, real `RoomLedgerRepository` ingest and real `Verifier`: a chore approved on device A pays on device B; a purchase on kid device B shows on A; a parent-only event forged on B is quarantined on A and visible through `observeQuarantined`.

## 5. Firebase transport, auth and App Check (core/sync-firebase)

- Firestore layout: `households/{hid}` + subcollections `members`, `devices`, `parentKeys`, `events/{eventId}` (create-only; a conflicting copy with a different hash is stored as `events/{eventId}__{hash}` so evidence survives), and one subcollection per docType (`chores`, `choreSubmissions`, `rewards`, `allowanceSchedules`, `savingsGoals`, `interestPolicy`, `kids`, `accounts`, `householdPolicy`). Top level: `linkCodes`, `challenges`, `deletionRecords` (functions only, no client access).
- `FirebaseSyncTransport`: push with batched writes (≤ 400 per batch), pull with `serverReceivedAt` cursors per collection (`FieldValue.serverTimestamp()` written by the client, ordered queries `> cursor`), `changes()` from snapshot listeners while the app is foregrounded (`ProcessLifecycleOwner`). Maps Firestore errors to `SyncError`.
- `FirebaseAuthSession`: sign-in (Credential Manager Google ID in release; email/password on the emulator in debug), anonymous sign-in for kid devices, claims refresh, sign-out. `HouseholdFunctions`: typed callable wrappers for §1.
- App Check: `PlayIntegrityAppCheckProviderFactory` in release, `DebugAppCheckProviderFactory` in debug. Functions enforce `request.app != null` unless `FUNCTIONS_EMULATOR`. D-M3-6.
- Bootstrap: `app` applies `com.google.gms.google-services` **only if `app/google-services.json` exists**; otherwise debug builds initialise `FirebaseApp` programmatically with `projectId = "demo-sprout"` and point Auth/Firestore/Functions at the emulator host from `BuildConfig.FIREBASE_EMULATOR_HOST` (gradle property `sprout.firebaseEmulatorHost`, default `10.0.2.2`). Release builds without `google-services.json` fail the build with a clear message. `INTERNET` permission added; a **debug-only** network security config permits cleartext to `10.0.2.2` and `localhost` only. Region: `europe-west1` for functions, Firestore `eur3` (PRIVACY TODO; D-M3-8).
- Tests: unit tests for the error mapping, cursor handling and batching with a fake Firestore facade; an opt-in Robolectric suite against the running emulator (`-Psprout.firebaseEmulator=true`) that pushes and pulls through the real SDK. Run locally before the PR; CI runs it in the backend job (emulator started with `firebase emulators:exec`).

## 6. App, onboarding and settings

- **Mode from the session**: a KID session (claims) shows kid mode for its `kidId` only and has no parent area; a PARENT session keeps the M2 behaviour (parent behind the lock, kid mode behind the exit gate). No session → onboarding.
- **Onboarding** (`feature/onboarding`): Welcome → "I'm a parent" (sign in → create household → PIN setup from `feature/lock`) or "This is a kid's device" (enter the 8-character code → register the device → done, lands in kid mode). A parent signing in on a second device whose uid already has a household goes to "Approve this device on your other phone" showing the fingerprint and waits for ACTIVE (listener). The parent side gets the approval sheet from a notification card on the dashboard ("New device waiting"). Linking a kid from the parent: Settings → Kids → kid → "Link a device" shows the code with the countdown.
- **Purge of the local household** (ADR-0004 §2): when a session is created and the database holds `householdId == "local"` data, show an explicit screen "Your trial data stays on this phone until you continue; it will be deleted" with a confirm; `PurgeLocalHouseholdUseCase` deletes kids, accounts, events, documents, outbox, pending actions, photos and audit rows of the local household in one transaction and records one audit row. Debug demo seeding (`HouseholdBootstrap`) runs only when there is no session.
- **Wipe on household gone** (`HouseholdGone`, deletion, or revoked device): `WipeLocalDataUseCase` closes the DB, deletes the database files, photos and the `SecretStore` blobs except the device key, clears the session, and restarts to onboarding with a message.
- **Settings**: Devices (list with role, attestation label, status, "Approve"/"Revoke"), Account (signed-in e-mail for parents, "Sign out"), Data ("Export household", "Delete household" with typed confirmation). Export writes the JSON bundle and a `ledger.csv` through `ACTION_CREATE_DOCUMENT`.
- **SyncWorker** (`app/work`): periodic 15 min + network constraint, plus an expedited one-off enqueue after each outbox insert (`OutboxDao` insert hook through `SyncTrigger`), plus `SyncEngine.run` while foregrounded. `AppInitializer` adds: restore session, install App Check, start sync, and `planUpToToday` runs only after the first successful pull of a session.
- Screens get Roborazzi goldens: onboarding (welcome, sign-in, code entry, waiting-for-approval), devices list, export/delete dialogs, "Rejected events" card.

## 7. Backend (`functions/`, `firestore/`)

- `firebase.json` + `.firebaserc` (`demo-sprout`), `firestore/firestore.rules`, `firestore/firestore.indexes.json`, `firestore/package.json` with `@firebase/rules-unit-testing` + `firebase-tools` pinned as devDependencies and a lockfile (D-M3-10), `npm test` = `firebase emulators:exec --only firestore "vitest run"`.
- Rules: household membership via `members/{uid}` (never from client data); `authorUid == request.auth.uid` and `authorDeviceId` is an ACTIVE device of that uid on every client write; events create-only with required fields and `schemaVersion in [1, 2]`; role gates per collection (kid writes only `choreSubmissions` with `payload.kidId == member.kidId` and status `SUBMITTED`, `events` with role KID); LWW enforced on document updates (`lamport` greater, or equal and `authorDeviceId` greater); `parentKeys` create by PARENT only, no update/delete by clients; `members`, `devices`, `linkCodes`, `challenges`, `deletionRecords` closed to clients (devices readable by members); size limits (payload ≤ 64 KB; events ≤ 16 KB). Rules tests: kid cannot approve, cross-household read denied, ledger immutable, unregistered or PENDING or REVOKED device rejected, lower-lamport update rejected, parent-key tamper rejected, link codes unreadable.
- Functions (TypeScript, Node 22 runtime, `firebase-functions` v2 `onCall`, `region: europe-west1`): the seven callables of §1 plus `onDeviceRevoked` cleanup. Attestation: parse the X.509 chain, verify to the Google hardware attestation roots (embedded, with the status list fetched and cached), check `attestationChallenge`, `attestationSecurityLevel`, key purpose SIGN and EC P-256, and that the leaf public key equals the submitted SPKI. Unit tests with `firebase-functions-test` against the emulator: each callable's happy path, code expiry/reuse/rate limit, attestation success with a recorded fixture chain and failure on a mismatched challenge, delete leaves only a `deletionRecords` row, export bundle shape. No PII in logs (`logger` calls carry ids and counts only).
- CI: new job `backend` in `ci.yml` (Node 24 with npm cache, JDK 17, cached emulator jars under `~/.cache/firebase/emulators`, `npm ci` + `npm run lint` + `npm test` in `functions/` and `firestore/`). It is **not** added to the required check for now (D-M3-11) but runs on every PR. The Android job unchanged (no `google-services.json` in CI).
