# Dependency verification

`verification-metadata.xml` records a SHA-256 checksum for every artifact the build downloads, and Gradle fails the build if anything differs. The file is generated, so it carries no comments. Renovate branches get it regenerated automatically by `.github/workflows/verification-metadata.yml`. After adding or bumping a dependency by hand, regenerate it with `./gradlew --write-verification-metadata sha256 help build detekt lint test --no-configuration-cache` (`help` alone misses artifacts resolved while tasks run, such as aapt2 and the Detekt and Lint classpaths) and review the diff before committing: new entries should match the change you made and nothing else, because a checksum written this way is trusted on first use. Dependency-Check also reads POMs the build never downloads; append `dependencyCheckAnalyze --continue` to that command to record them (the analysis itself still needs `NVD_API_KEY` and fails without it, but the checksums are written). Gradle only adds entries; do not regenerate from an empty file on a warm local cache, because parent POMs and BOMs that a cold CI runner downloads would then be missing.

## Artifacts only the IDE resolves

Android Studio sync resolves a few artifacts that no CLI task touches, and strict verification rejects the sync until they are recorded: the Gradle source distribution (`gradle:gradle:<version>` `-src.zip` from services.gradle.org) and the metadata of the Groovy modules bundled with Gradle (`org.apache.groovy:groovy-*` from repo.gradle.org), which Gradle's `DefaultGradleApiSourcesResolver` fetches while building the IdeaProject model for `build-logic` because it depends on `gradleApi()`. Studio always passes `-Didea.gradle.download.sources=true`, so the `idea.gradle.download.sources` property in `gradle.properties` does not stop it. After a Gradle upgrade, record them again: run a small Gradle Tooling API client against the project that requests `IdeaProject` for the root build and for `build-logic` with `--write-verification-metadata sha256 --no-configuration-cache` and `-Didea.gradle.download.sources=true`, then cross-check every new checksum against the `.sha256` files on repo1.maven.org (and services.gradle.org for the source zip) before committing. Trust rules were deliberately not widened for these.

## Platform-specific artifacts

`com.android.tools.build:aapt2` ships one jar per OS and Gradle only resolves the one for the machine running the build, so a macOS regeneration records the `-osx` jar alone and CI on Linux then fails verification. After every AGP bump, add the `-linux` and `-windows` entries by hand using Google's published checksums: `https://dl.google.com/dl/android/maven2/com/android/tools/build/aapt2/<version>/aapt2-<version>-<os>.jar.sha256`.
