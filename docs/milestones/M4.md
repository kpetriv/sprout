# M4: E2EE chat and time bank

Scope from `docs/PLAN.md` M4: key agreement, encrypted threads, Seedling presets and voice notes, key rotation on device removal, time bank timer with a visible notification. Builds on M3's registry, signed documents, sync lanes and the Sprout server. Decisions taken with defaults are logged as D-M4-* in `docs/DECISIONS-PENDING.md`.

Constraints that shape the design:
- **Spark plan, no Cloud Storage.** New Firebase Storage buckets need Blaze (D-M3-29/38). Photos and voice notes travel as encrypted chunks in Firestore (§4).
- **Only `core/sync-firebase` talks to Firebase.** New lanes go through `SyncTransport`.
- **The server holds no secrets.** It verifies signatures and enforces membership; it never sees a plaintext or a thread key.
- **Receivers trust the registry, never a claim.** Every encryption key is bound to a registered device by a device-key signature that receivers verify themselves.
- **minSdk 28.** JCE `XDH` is only reliable from API 33; `core/crypto` needs a fallback (§1.1).

## 1. Keys (`core/crypto`, `core/domain-ledger`)

### 1.1 Device encryption key
- Each device holds one X25519 key pair, generated on first use; the private scalar is a 32-byte secret in `SecretStore` under `chat.x25519.v1` (Keystore-wrapped, wiped with the rest, except that a parent's sign-out wipe keeps it with the device key and a record of the device's own chat counters for the same device id, and onboarding stashes it before a new registration; D-REL-6, D-REL-7, D-REL-27 to D-REL-33). Public key: raw 32 bytes (`X25519PublicKey`).
- `X25519KeyAgreement` gets a pure-Java fallback for API < 33 (Tink's `com.google.crypto.tink.subtle.X25519` via `tink-android`, pinned in the catalog with verification metadata; D-M4-1). `JceX25519KeyAgreement` stays preferred when `XDH` is available. One test vector suite runs against both.
- **Binding.** `EncryptionKeyBinding = sign_P256(device key, "sprout/device-encryption-key/v1" || 0x00 || hid || 0x00 || deviceId || 0x00 || x25519pub)`. The server stores `encryptionKey` (base64, 32 bytes) and `encryptionKeySignature` on the device row only after verifying the signature against the device's registered P-256 key; receivers verify it again when they read the registry (`RegisteredDevice.encryptionKey: BoundEncryptionKey?` with `verify(check)`), and ignore a key whose binding fails.
- Registration: `createHousehold`, `registerParentDevice`, `redeemLinkCode` accept optional `encryptionKey` + `encryptionKeySignature`; devices registered before M4 call the new `registerEncryptionKey` callable (device-proof signed, idempotent, `permission-denied` if the device already has a different key; a changed key needs a re-registration, D-M4-2).

### 1.2 Thread keys
- One thread per kid; `threadId = kidId`. Members of a thread: every ACTIVE PARENT device of the household and every ACTIVE KID device whose `kidId` is the thread's kid. Kid mode on a parent phone (D-M3-12) uses the parent device's keys.
- A thread key is a random 32-byte AES-256-GCM key per (thread, epoch), generated by a PARENT device. It is distributed as a signed `thread_key` document (`DocTypes.THREAD_KEY`, PARENT-writable, docId `"<kidId>.<epoch>"`, immutable in practice; LWW by the existing resolver only matters if two parents race on the same epoch, D-M4-3):
  ```
  payload = { threadId, epoch, createdByDeviceId,
              wraps: { <deviceId>: { wrapped: base64 } ... } }
  ```
  `wrapped = AesGcm(wrapKey, threadKey, aad = "sprout/thread-key-wrap/v1" || 0x00 || hid || 0x00 || threadId || 0x00 || epoch || 0x00 || senderDeviceId || 0x00 || recipientDeviceId)` with `wrapKey = HKDF(X25519(sender priv, recipient pub), salt = sha256(hid), info = "sprout/thread-key-wrap/v1" || threadId || epoch)` via `HouseholdKeyDerivation`. Static-static ECDH: no forward secrecy; accepted and documented (D-M4-4). The sender wraps for itself too.
- **Epoch rules** (`ThreadKeyPolicy`, pure Kotlin, tested):
  - Epoch 0 is created by the first PARENT device that has an encryption key when a kid exists.
  - **Addition** (new ACTIVE member with an encryption key): any PARENT device re-wraps the *current* epoch for it (a new `thread_key` doc with the same epoch, superset of wraps; LWW is safe because every doc for an epoch wraps the same key).
  - **Removal** (a member device becomes REVOKED, or a kid is archived): the next PARENT device to notice creates epoch+1 wrapped only for the remaining members. Senders always encrypt with the highest epoch they can unwrap whose wrap set contains no device they know to be REVOKED. A device that cannot unwrap the latest epoch shows "waiting for a parent device" and does not send.
  - Receivers keep every epoch key they could unwrap (local `thread_keys` table, encrypted at rest by SQLCipher like everything else) so old messages stay readable.
- `ThreadKeyring` (core/crypto + domain): `unwrap(doc, myDeviceId, myPriv, senderPub)`, `wrapFor(members)`, `latestUsable(threadId)`.

### 1.3 Message envelope
New signed envelope, not the document envelope (messages are immutable, kid-readable only in their own thread, ordered):
```
MessageEnvelope(schemaVersion = 1, householdId, threadId, messageId (uuid),
                authorUid, authorDeviceId, authorRole, seq (per author device per thread, monotonic from 1),
                lamport, createdAt (epoch ms), epoch, kind: TEXT | PRESET | VOICE | PHOTO,
                ciphertext (bytes), blobId?, signature)
```
- `signature = ECDSA(device key, "sprout/message/v1" || 0x00 || canonical(envelope minus signature))`; `ciphertext = AesGcm(threadKey[epoch], plaintext, aad = "sprout/message/v1" || 0x00 || canonical(header fields))` so a ciphertext cannot be transplanted between envelopes.
- Plaintext (canonical JSON): `{ "text": ... }` (TEXT, ≤ 1000 chars), `{ "preset": "<id>", "emoji": "<optional>" }` (PRESET), `{ "durationMs": n }` (VOICE, bytes in a blob), `{ "photoRef": {...}, "caption"? }` (PHOTO, bytes in a blob). Ciphertext ≤ 8 KB in rules.
- Verification (`MessageVerifier`, mirrors `RemoteEventVerifier`): registry lookup of the author device, `acceptsLamport`, role/thread rule (KID devices only in their own thread), signature, `seq` continuity per (author device, thread) with gaps **held** (like held events) and duplicates ignored, lamport jump bound. Quarantine reasons reuse `QuarantineReason` plus `WRONG_THREAD`, `SEQ_GAP`.
- Decryption failures are not quarantines: a message whose epoch key is missing stays "locked" and is retried when a key arrives.

## 2. Blobs (photos and voice notes)
- `blobs` subcollection, create-only, author-device signed. A blob is ≤ 2 chunks of ≤ 700 KB **Bytes** fields (Firestore `bytes`, rules check `.size()`), total ≤ 1.4 MB. Docs: `blobs/{blobId}.{householdId, threadId?, kidId, authorUid, authorDeviceId, lamport, chunk (0..1), chunks (1..2), data (bytes), sha256 (of the whole ciphertext), epoch, signature}`; docId `"<blobId>.<chunk>"`; signature over the canonical header plus `sha256(data)` per chunk. `threadId` set for chat blobs; chore photos carry `kidId` and `submissionId` instead and are encrypted with the thread key of that kid (the parent approves them; same members), D-M4-5.
- Client-side limits before encryption: photos downscaled to ≤ 1280 px, JPEG q80, target ≤ 500 KB; voice notes ≤ 30 s AAC-LC 32 kbps (~120 KB).
- **Chore photo upload** (closes D-M2-3/D-M3-9): the kid device uploads the submission photo as a blob when the thread key is available; the submission's `photoRef` gains `blobId`. Parent approvals download, verify sha256, decrypt and show it; "Photo on the kid's device" remains the fallback while the blob is absent. Local photo bytes stay encrypted with the per-install key until uploaded, then are deleted on decision as today. The orphan sweep from D-M2-14 is added at startup.
- Blobs are pulled on demand (`SyncTransport.fetchBlob(blobId)`), not in the regular pull; a local `blobs` cache table (encrypted files under `noBackupFilesDir/blobs/`) with LRU eviction at 50 MB.
- `exportHousehold` includes messages and blob metadata (ciphertext omitted, D-M4-6); `deleteHousehold` already deletes subcollections.

## 3. Sync lanes (`core/sync`, `core/sync-firebase`, `firestore/`, `server/`)
- `SyncTransport.push(events, documents, messages, blobs)`, `pull(cursor)` returns `messages` too (per-household cursor key `messages`), `fetchBlob(blobId)`, `changes()` covers `messages`. `OutboxItem.Kind` gains `MESSAGE`, `BLOB`. Push order stays head-of-line per device; a blob is pushed before the message that references it.
- `FakeBackend` gains `messages` and `blobs` collections mirroring the rules (including kid read scoping) and `encryptionKey` on registered devices; `FakeBackendRulesTest` extended.
- **Firestore rules**: `messages/{id}` create-only by an ACTIVE device of the caller, closed key set, `ciphertext.size() <= 8192`, `authorRole == m.role`, KID requires `threadId == m.kidId`; **read**: PARENT members read all, KID members read `resource.data.threadId == m.kidId`. `blobs/{id}` create-only, `data.size() <= 716800`, KID requires `kidId == m.kidId`; read like messages (chore-photo blobs readable by parents and the kid). `threadKeys` is a document collection (`docTypes()` entry, PARENT-only writer, closed payload: `threadId`, `epoch` int, `createdByDeviceId`, `wraps` map ≤ 16 entries of `{wrapped}` strings ≤ 128). Device docs gain `encryptionKey`/`encryptionKeySignature` (server-written only). Budget tests for the largest message, blob chunk and thread-key doc. Indexes for `messages` and `blobs` (authorDeviceId asc, lamport desc; serverReceivedAt asc).
- **Server**: registration callables accept the encryption key pair of fields (verify binding with the submitted/registered P-256 key); `registerEncryptionKey` callable (`sprout/register-encryption-key/v2` proof, device-proof pattern); `DOCUMENT_COLLECTIONS` gains `threadKeys`; `maxLamport` scans include `messages` and `blobs`; export covers them; `revokeDevice` unchanged (rotation is client-driven; D-M4-7). Rate limit `registerEncryptionKey` like `registerParentKey`.
- `docs/FIREBASE.md` tables updated.

## 4. Database (`core/database`, schema v6)
Tables: `messages` (envelope columns + `plaintext` nullable, decrypted on apply when a key exists; `status` RECEIVED | LOCKED | QUARANTINED | HELD), `message_seq` (per thread per author device next seq), `thread_keys` (threadId, epoch, key bytes, source doc), `blobs` cache index, `photos.blobId`. `RoomRemoteApplier.applyMessages`, `applyDocuments` handles `THREAD_KEY` (unwrap on apply; re-try LOCKED messages when a key arrives). `DocumentWrites.appendMessage` allocates seq + lamport and the outbox row in one transaction. Wipe and purge cover the new tables, `chat.x25519.v1`, blob files (a sign-out wipe keeps `chat.x25519.v1`, D-REL-6). Migration tests.

Time bank use cases (closes "no writer"): `StartTimeBankUseCase` (kid-authored `TimeBankStarted`, refuses when `TimeBankState.running` or balance ≤ 0), `StopTimeBankUseCase(minutesUsed)` (kid-authored `TimeBankStopped`, `minutesUsed = min(elapsed whole minutes, balance)`), `ReconcileTimeBankUseCase` (on start-up: a running session older than its balance is stopped with `minutesUsed = balance`; D-M4-8). Elapsed time is computed from `TimeBankState.startedAt` (envelope `createdAt`), not from a process timer.

## 5. Features
### 5.1 `feature/chat`
- Ports: `ChatThreads` (threads with kid name/avatar, unread counts), `MessageReader` (page by thread), `MessageSender(threadId, plaintext kind…)`, `VoiceRecorder`, `BlobLoader`, `OutgoingMessageFilter` (kindness hook, no-op default; M6 fills it), `ThreadKeyStatus` (usable / waiting-for-parent).
- Parent: thread list + thread screen (text, photo attach from the gallery, voice playback). Behind the parent gate; `SecureWindow`.
- Kid, three tiers: Seedling = preset tiles (12 presets with emoji, `strings.xml`), emoji row, voice note (hold to record, ≤ 30 s), read-aloud on tap (`ReadAloud` bound to Android TTS in app); Sprout = free text with the filter hook + presets; Sapling = free text. All three: photo view, locked-message placeholder ("Waiting for a parent device"), send states.
- Screenshot tests per tier and per state (empty, messages, locked, recording, sending-failed); ViewModel tests with fakes.

### 5.2 `feature/timebank`
- Kid screen, three tiers: Seedling = big Start/Stop sun with a draining ring and whole minutes; Sprout = timer, remaining minutes, today's sessions; Sapling = timer plus history and the rule text. Parent view in the wallet is out of scope (the ledger already shows sessions).
- Ports: `TimeBankControl(start, stop)`, `TimeBankClock`. Running state is derived from the ledger projection; the screen ticks locally.
- Screenshot tests per tier and state (idle, running, empty balance).

### 5.3 App wiring (`app/`)
- Navigation: kid home gains Chat and Screen time buttons; parent home gains Chat.
- **Notifications**: channel `timebank` (ongoing, silent) and runtime `POST_NOTIFICATIONS` request on first Start (declined → the timer still works, no notification). **No foreground service** (D-M4-9): an ongoing notification with a chronometer is posted on Start and cancelled on Stop; a WorkManager one-time job (delay = remaining balance) auto-stops the session and the start-up reconcile covers process death. Exact alarms are not used.
- Encryption key: generated and registered during onboarding registrations; for devices linked in M3, `AppInitializer` step after reconcile registers it (`registerEncryptionKey`) with retry on the next sync.
- `ThreadKeyRotation` driver (parent sessions only): after each successful pull, compares thread membership with the latest epoch's wrap set and publishes re-wraps/rotations per §1.2. Blob upload worker for pending chore photos and chat blobs. New work names registered in `WorkManagerBackgroundWork` for cancellation on removal.
- TTS `ReadAloud` implementation (Android `TextToSpeech`, kid locale), bound in kid mode.
- Two-emulator walk: parent + kid exchange text, preset, voice note and photo; chore photo now visible on the parent; revoke the kid device → parent rotates (epoch+1), a re-linked kid device cannot read old messages' plaintext? (it can read messages wrapped for its *new* device only: old epochs are not re-wrapped for new devices, D-M4-10) and the revoked one cannot read new ones; time bank start, notification visible, stop, balance debited; auto-stop at zero.

## 7. Verification
- Unit: key binding verify/reject; wrap/unwrap both providers; epoch policy (addition re-wrap, removal rotation, revoked exclusion); message verifier (wrong thread, seq gap held, duplicate, bad signature, transplanted ciphertext fails AEAD); time bank use cases incl. reconcile.
- Convergence (core/database `ConvergenceTest` style, two real Room devices over `FakeBackend`): parent and kid exchange messages; the backend only ever holds ciphertext (assert no plaintext substring in `FakeBackend.messages()`/`blobs()`); revoke the kid device → rotation → the revoked device's engine cannot decrypt epoch+1 messages; a second parent device added later can read the current epoch.
- Rules: kid cannot read another kid's thread or blobs; kid cannot write to another thread; blob chunk over size rejected; threadKeys writer PARENT only; budget tests.
- Server: encryption key binding verified; `registerEncryptionKey` proof and idempotency; export includes messages.
- Gate: `./gradlew build detekt lint test verifyRoborazziDebug --no-daemon`; `server`/`firestore` `npm test`; emulator transport suite once; the walk in §5.3.

## As built (2026-11-03)

The spec above is kept as written. What was built differs from it as follows; the reasoning is in the D-M4 rows of `docs/DECISIONS-PENDING.md` and in ADR-0008.

**Walk (2026-11-03, two emulators against the local emulators and `npm run dev`).** Parent onboarding (trial PIN and fingerprint, sign-in, create household, purge, signing) and a Seedling kid linked by code; both devices registered their encryption key (`encryptionKey.registered` for the PARENT and the KID device in the server log). Parent text → kid (read-aloud spoke it through the device's TTS) → kid preset with emoji → parent; parent photo from the picker → kid (blob fetched, verified and cached). Kid (Sprout tier) submitted a chore with a camera photo: the blob and the re-signed submission with `photoRef.blobId` reached Firestore and the parent's approvals inbox showed the photo itself. Time bank: Start posted the silent ongoing notification (channel `timebank`, countdown), Stop after a minute debited 1 minute and removed it. Revoking the kid phone made the parent publish epoch 1 wrapped for the parent device only; the next parent message used epoch 1; the backend held ciphertext only; the revoked phone erased its database, blob cache and secrets on its next launch. Logcat: no message text, kid name, key material or chore titles; the only e-mail lines are the Firebase Auth SDK's (D-M3-40).

**Audit 2 (fix pass 3).** The second security audit found no Critical or High issues and three Mediums, all fixed: chore photo blobs are bound to the submission on screen (A2-M1); decrypted voice notes play from memory, recording temp files are deleted on every path and swept at start-up, and the wipe clears `cacheDir` (A2-M2); the outbox runs a ledger lane and a chat lane, and blob chunk refusals are transient (A2-M3, D-M4-22). Lows fixed with them: late messages are ordered and clamped and labelled "Arrived late" (A2-L1), a refused thread key's ack and audit row land in one transaction so a crash cannot confirm it (A2-L3), a media message and its blob are queued together (A2-L4), read-aloud asks for offline synthesis and the docs say the text goes to the system TTS engine (A2-L5, D-M4-23), registry pinning covers uid, role and kid (I1), a replaced chat key on this phone shows "remove and re-link" instead of waiting (I2), and the `PullPage.malformed` KDoc matches the code (I3). Deferred: the re-wrap gap for freshly linked devices (A2-L2, M5 or M7) and a monotonic-clock check for the time bank (I4, D-M4-24, M7).

**Open at the end of M4:** voice notes were not walked on the emulator (the emulator froze whenever the microphone opened on this host; the send, fetch and decrypt path is covered by `ChatAdaptersTest`), so neither recording nor parent playback is verified on a device; the auto-stop at zero was not walked (unit-tested delay, worker untested on a device); the `RECORD_AUDIO` and `POST_NOTIFICATIONS` prompts were not walked (the walk installed with every permission granted); the revoked phone's removed screen names "household deleted or no longer part of it" rather than "a parent removed this phone" (M3 behaviour for a disabled kid account); no in-app recovery for a device whose encryption key conflicts (D-M4-14; the chat now says so and asks for a re-link); no forward secrecy (D-M4-4); a household with no parent device online cannot rotate.

**Walked in v1 (slice W, 2026-11-04, [v1 walk](M8.md#v1-emulator-walk-slice-w-2026-11-04)):** the `RECORD_AUDIO` prompt (deny, then allow) and the `POST_NOTIFICATIONS` prompt on the first Start; voice notes recorded on the kid's phone (the emulator no longer froze with the default audio settings), the 30 s cap, parent playback, no voice file left on either phone; the auto-stop at zero, also with the app's process killed during the session. Still open: voice notes on a phone with a real microphone (P6) and the auto-stop after a reboot (P7 step 4); the rest of the list above is unchanged.
