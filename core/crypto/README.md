# core/crypto

Byte-oriented crypto primitives for Sprout. Every primitive sits behind a small interface: JVM unit tests use the pure-JCE implementations, and `di/CryptoModule` binds the Android Keystore ones in the app. In-memory fakes live in `src/testFixtures`, never in `main`; other modules use them through `testImplementation(testFixtures(projects.core.crypto))` (and `androidTestImplementation(...)` for instrumented tests). The primitives know nothing about ledger events or chat messages; callers pass canonical bytes in and get bytes out. The one exception is the `chat` package (M4), the glue that applies them to the chat wire formats defined in pure Kotlin in `core/domain-ledger` (`domainledger.chat`), which is why this module depends on `core/domain-ledger`.

The module never logs, so no key material, PIN, or plaintext can reach a log. `toString` on every secret-holding type prints `<redacted>`.

## Primitives

| Interface | Production (Hilt) | JVM / tests | Notes |
|---|---|---|---|
| `DeviceKeyStore` | `AndroidKeystoreDeviceKeyStore` | `InMemoryDeviceKeyStore` (test fixture) | EC P-256, StrongBox first and TEE if StrongBox refuses, SHA-256 only, **no user auth** (background sync must sign). `DeviceSigner` is the entry point for signing. `keyProperties()` returns self-reported `KeyInfo` (`DeviceKeyProperties`), **not attestation**. The M1 key is provisional: M3 generates the household identity key at link time with `setAttestationChallenge`. |
| `ParentAuthorizer` | `KeystoreParentAuthorizer` over `AndroidKeystoreParentAuthKeyStore` | `FakeParentAuthorizer` (test fixture, software key) | Parent signatures on parent-only events (ADR-0004 §1). `availability()`; `existingParentPublicKey()` (read only, **never creates**); `createParentKey()` (suspend, creates; throws `ParentAuthUnavailableException(availability)` without a strong biometric; **only** `feature/lock`'s PIN-gated `ParentKeyEnrolment` / `ParentKeyRenewal` call it, audit H1); `parentPublicKey()` is `@Deprecated` (still creates lazily, kept only so `RegisterParentKeyUseCase.invoke()` compiles until the data layer drops it); `initSignature()` returns a fresh `Signature` for a `BiometricPrompt.CryptoObject` (throws `ParentKeyInvalidatedException` after an enrolment change); `resetParentKey()`. A local key is never trusted on its own: callers compare it byte-for-byte with the household's registered key and verify against the registered key; an event signed by any other key counts as unsigned. `ParentSigner.sign(authorizedSignature, payload)` returns DER; `verifyParentSignature(parentPublicKey, payload, signature)` checks it with `JceEcdsaVerifier`. The fake's signatures sign once, like a per-use key. No UI in this module. |
| `ParentAuthKeyStore` | `AndroidKeystoreParentAuthKeyStore` | none | Keystore lifecycle of `sprout.parent.auth.v2`: EC P-256, per-use authorisation, `AUTH_BIOMETRIC_STRONG` only on API 30+, invalidated on enrolment change (see Caveats for API 28–29). Key creation refused by Keystore becomes `ParentAuthUnavailableException`, with any partial entry deleted. |
| `ParentAuthAvailabilityChecker` | `BiometricParentAuthAvailabilityChecker` | lambda (`fun interface`) | `androidx.biometric` `BiometricManager.canAuthenticate(BIOMETRIC_STRONG)` mapped to `ParentAuthAvailability`: `STRONG_BIOMETRIC_AVAILABLE`, `NOT_ENROLLED`, `NO_HARDWARE`, `UNAVAILABLE_OTHER` (everything else, including a failing query). Anything but the first means no `parentSignature` on this device (D-M2-1). |
| `Signer` / `Verifier` | `JceEcdsaSigner` / `JceEcdsaVerifier` | same; `generateSoftwareSigningKey()` (test fixture) | ECDSA P-256 / SHA-256, DER signatures, X.509 SPKI public keys (`PublicKeyBytes`). The verifier rejects keys on other curves and returns false for any malformed input; it never throws on untrusted bytes (every `GeneralSecurityException` and `RuntimeException` means "not valid"). |
| `Aead` | `AesGcmAead` | same | AES-256-GCM, 12-byte `SecureRandom` nonce per call, 128-bit tag. Output `0x01‖nonce‖ciphertext‖tag`; the version byte is bound into the tag (GCM associated data is `version‖associatedData`), and unknown versions are rejected. Associated data must be non-empty (`IllegalArgumentException` otherwise). |
| `X25519KeyAgreement` | `X25519KeyAgreements.select(random, Build.VERSION.SDK_INT)`: `JceX25519KeyAgreement` from API 33 when JCE `XDH` passes the RFC 7748 §6.1 self-test, `TinkX25519KeyAgreement` otherwise (D-M4-1) | both | X25519 (RFC 7748) on raw 32-byte keys; rejects all-zero shared secrets. Both implementations give identical results, so a stored key survives an OS update that switches them. Named for the curve so it does not clash with `javax.crypto.KeyAgreement`. |
| `EncryptionKeyStore` | `SecretStoreEncryptionKeyStore` | same over the in-memory `SecretStore` fixtures | The device's X25519 chat key pair (M4 §1.1): the private scalar is the `SecretStore` secret `chat.x25519.v1` (created on first use unless `createIfMissing = false`), the public key is computed. Close the returned `X25519KeyPair`. |
| `Hkdf` | object | same | HMAC-SHA256 extract and expand (RFC 5869). |
| `HouseholdKeyDerivation` | `@Inject` | same | `deriveThreadKey(sharedSecret, salt, info)`: HKDF with a versioned domain label, giving a 32-byte AES key (M4). |

## Chat (`chat` package, M4)

| Class | What it does |
|---|---|
| `EncryptionKeyBinding` | Signs `EncryptionKeyBindingPayload` (`"sprout/device-encryption-key/v1" 0x00 hid 0x00 deviceId 0x00 x25519pub`) with the active device key (`sign`, through `DeviceSigner`) or a pending registration key (`signWith`). Receivers verify with `BoundEncryptionKey.verify` / `RegisteredDevice.verifiedEncryptionKey` (`core/domain-ledger`); `Verifier.asSignatureCheck()` adapts the JCE verifier. |
| `ThreadKey` | AES-256-GCM key of one (thread, epoch); `AutoCloseable`, redacted `toString`, `copyBytes`/`fromBytes` for the encrypted database. |
| `ThreadKeyring` | `newKey`, `wrapFor(householdId, key, sender, senderPrivate, members)` → `ThreadKeyDocument`, `unwrap(householdId, doc, myDeviceId, myPrivate, senderPublic)`, exactly as `ThreadKeyWrapFormat` documents (static-static X25519, HKDF salt `SHA-256(hid)`, AAD binding household, thread, epoch, sender and recipient). Which epoch to create, re-wrap or send with is `ThreadKeyPolicy` (pure, `core/domain-ledger`). |
| `MessageCipher` | AES-GCM of the canonical `MessagePlaintext` under the thread key, AAD `MessageHeader.associatedData()`; ciphertext ≤ 8192 bytes. Decryption failures are `MessageDecryptionException`, never a quarantine. |
| `MessageSigner` | Device-key signature over `MessageEnvelope.signedPayload()`. |
| `BlobCipher` | One AEAD ciphertext per photo or voice note (AAD `BlobContext.associatedData()`), split into ≤ 2 chunks of ≤ 700 KiB; decryption checks the whole-ciphertext SHA-256 first. |
| `PinPepper` | `KeystoreHmacPepper` | `InMemoryHmacPepper` (test fixture) | `HMAC-SHA256(key, utf8(pin))` with a non-exportable 256-bit Keystore HMAC key, purpose SIGN, no user auth, StrongBox first. `apply` creates the key on first use (hashing); `applyExisting` never does (verifying), so a lost key throws `PinPepperUnavailableException` instead of reading as a wrong PIN. |
| `PinHasher` | `Argon2idPinHasher(random, dispatcher, pepper)` (m=64 MiB, t=3, p=1) | `Pbkdf2PinHasher(random, dispatcher, pepper)` (600,000 iterations) | The slow hash runs over the pepper output (ADR-0004 §3). Encoded `v2$<alg>-pepper$<params>$<saltB64>$<hashB64>` (`argon2id-pepper`, `pbkdf2-sha256-pepper`; PBKDF2 gets the 32 pepper bytes as 64 hex chars). The unpeppered M1 format `v1$…` is **retired** (no M1 build shipped, audit L5): `verify` throws `UnsupportedPinHashException` (an `IllegalArgumentException`: "reset required") without checking the PIN, `PinHash.parse` returns null for it, `PinHash.isRetiredFormat` recognises it, and `needsRehash` is true for anything but a current-parameter `v2` hash of the hasher's own algorithm. 16-byte salt, 32-byte hash, constant-time compare; parsing accepts only 16–64-byte salts and hashes. The Argon2 hasher also verifies peppered PBKDF2 hashes. |
| `PinLockoutPolicy` | `@Inject @Singleton` (`LockoutStateStore`, `BootClock`, `ParentKeyHealth`) | same with `InMemoryLockoutStateStore` and `FakeBootClock` (test fixtures) and a lambda for `ParentKeyHealth` | Stateful and persisted: `decision()`, `registerFailure()`, `registerSuccess()`, `registerBiometricSuccess()` returning `LockoutDecision` (`Allowed`, `Wait(remaining)`, `RequireBiometric`). Lockouts of 0, 0, 0, 30 s, 60 s, 120 s … From failure 11 (where the schedule reaches the 1 h cap) the decision is `RequireBiometric` **only while `ParentKeyHealth.biometricUnlockUsable()`** (strong biometric usable, a parent key registered, this device's key equal to it and not invalidated; `feature/lock`'s `ParentKeyStatusCheck` implements it). Otherwise, or if the check throws, the cap is a 1 h wait per failure, so the PIN path never closes permanently (audit H2). Measured with elapsed realtime and the boot id, never the wall clock; see Caveats for reboots. |
| `LockoutStateStore` | `EncryptedLockoutStateStore` (`SecretStore` secret `pin.lockout`, `Aead`, `FilesDirBlobStorage` blob `pin.lockout.state`) | `InMemoryLockoutStateStore` (test fixture); the encrypted store also runs on the JVM over the in-memory fixtures | Failure count, lockout start (elapsed realtime) and boot id, AES-GCM encrypted with associated data `sprout/pin-lockout-state/v1`. A state that does not decrypt or parse is `LockoutStateUnavailableException`, which the policy treats as the cap. |
| `BootClock` | `AndroidBootClock` | `FakeBootClock` (test fixture, `advanceBy`, `setElapsed`, `reboot`) | `SystemClock.elapsedRealtime()` plus `/proc/sys/kernel/random/boot_id` read once per process (fallback `Build.FINGERPRINT + Build.TIME`). |
| `SecretStore` | `WrappedSecretStore` + `AndroidKeystoreKeyWrapper` + `FilesDirBlobStorage` | `WrappedSecretStore` + `InMemoryKeyWrapper` + `InMemoryBlobStorage` (test fixtures) | Random 32-byte secrets (for example the SQLCipher passphrase), wrapped with AES-256-GCM. The secret's name is bound in as associated data. If a stored secret cannot be unwrapped, this throws; it never regenerates the secret. `getOrCreate(name, createIfMissing = false)` throws `SecretUnavailableException` instead of creating a missing secret; the database layer passes `createIfMissing = !databaseFileExists` so a lost blob cannot orphan an existing database. |

Secrets (`SymmetricKey`, `SharedSecret`, `X25519PrivateKey`) are `AutoCloseable` and zero their bytes on `close()`. Copies made inside JCE are outside this guarantee.

## Key aliases (`KeyAliases`)

| Alias | Type | User auth | Purpose |
|---|---|---|---|
| `sprout.device.signing.v1` | EC P-256 sign/verify | No | Signs every ledger event and chat message this device writes (provisional until M3's attested household identity key) |
| `sprout.parent.auth.v2` | EC P-256 sign/verify | Yes, per use (timeout 0), `AUTH_BIOMETRIC_STRONG` only (API 30+) | `parentSignature` on parent-only ledger events (ADR-0004), one `BiometricPrompt` per event |
| `sprout.pin.pepper.v1` | HMAC-SHA256, 256-bit, sign | No | Peppers the parent PIN before Argon2id/PBKDF2 |
| `sprout.secret.wrap.v1` | AES-256-GCM | No | Wraps local secrets such as the SQLCipher passphrase |

**Retired, never reuse:** `sprout.parent.auth.v1` (M1: 30-second validity window, device credential accepted). It was replaced by `sprout.parent.auth.v2` before any production use and its code path is removed. A development device may still hold a key under it; nothing reads it. Reusing the alias for another policy could pick up such a stale key.

All of them are generated through `AndroidKeystore.generate`: StrongBox first when the device has it; if StrongBox throws a `ProviderException` (including `StrongBoxUnavailableException`) or a `KeyStoreException`, any partial entry under the alias is deleted and generation repeats in the TEE (`withStrongBoxFallback`, unit tested with lambdas).

Wrapped blobs live in `noBackupFilesDir/sprout_secrets/<name>.bin` and are written atomically.

## Threat model coverage ([docs/THREAT_MODEL.md](../../docs/THREAT_MODEL.md))

| Threat | What this module provides |
|---|---|
| T1 Kid forges parent actions | `ParentSigner` / `verifyParentSignature`: parent-only events carry a signature from the strong-biometric-bound parent key; with the registered public keys (M3) receivers reject events a kid device key signed |
| T3 Forged author or device | Device signing key (non-exportable, hardware-backed) and `Verifier` |
| T4 Local DB edits on a rooted device | `SecretStore` provides the Keystore-wrapped SQLCipher passphrase |
| T5 Operator reads chat | `X25519KeyAgreement`, `HouseholdKeyDerivation`, and `Aead` are the building blocks for E2EE (wired up in M4) |
| T7 Stolen parent phone | **Addressed in M2 pending registry (M3).** Peppered Argon2id PIN hash (a dumped hash cannot be brute-forced off-device), a lockout that survives process death and reboots and closes the PIN path at the cap (`RequireBiometric`, only while a biometric unlock can succeed; otherwise a 1 h wait per attempt), and a per-use, strong-biometric-only parent key, so knowing the screen lock or the app PIN is not enough to sign a parent-only event. Receivers can only reject unsigned or wrongly signed events once the parent-key registry exists (M3). |
| T9 PII in logs | No logging in this module; redacted `toString` on secrets |
| T10 Supply chain | argon2kt, `androidx.biometric` 1.1.0 and `tink-android` (X25519 fallback only) are pinned in the version catalog and checksummed in `gradle/verification-metadata.xml`; argon2kt's unused `androidx.appcompat` runtime dependency is excluded (biometric keeps appcompat, which its API 28 fingerprint dialog uses) |
| T13 In-transit modification | Signatures and AEAD detect modification independently of TLS |
| T14 Backup extraction | Keystore keys are non-exportable; wrapped blobs go in `noBackupFilesDir` |
| T16 Parent repudiation | **Addressed in M2 pending registry (M3).** Each parent-only event gets its own strong-biometric prompt through a per-use `CryptoObject` (`sprout.parent.auth.v2`); the device credential cannot authorise it. The signature becomes evidence against a registered key once M3 builds the registry. |
| T17 Removed device reads chat | Thread keys come from HKDF with an epoch in `info`; rotation means a new epoch (M4) |

## Caveats for consumers

- **ECDSA malleability.** `(r, s)` and `(r, n−s)` both verify. Hash chains and event ids must be computed over the payload, never over signature bytes.
- **X25519 on Android.** JCE `XDH` comes from Conscrypt from API 33; below that `CryptoModule` binds Tink's pure-Java X25519 (D-M4-1). The selection also runs an RFC 7748 self-test, so a broken provider falls back too.
- **Chat keys have no forward secrecy** (D-M4-4): wraps are static-static X25519, so a device that held an epoch key can read that epoch for good; rotation protects new messages only.
- **Parent key and `CryptoObject`.** The key is per use: call `ParentAuthorizer.initSignature()` for every event, wrap it in a `BiometricPrompt.CryptoObject`, prompt with `BIOMETRIC_STRONG` only (no `DEVICE_CREDENTIAL`), and pass `result.cryptoObject.signature` to `ParentSigner.sign`. A `Signature` used once, or never authorised, fails with a `GeneralSecurityException`.
- **Parent key lifecycle (audit H1/H2).** Nothing creates the key lazily. It is created, proven with one prompt and registered only by `feature/lock`'s `ParentKeyEnrolment.enrol(pin)` (fresh PIN under the lockout, refuses to replace a registered key), and replaced only by `ParentKeyRenewal.renew(pin)` after `ParentKeyInvalidatedException` (fingerprint added or removed). Exceptions consumers map: `ParentKeyInvalidatedException` (open) and its subclass `ParentKeyMismatchException` (the local key is missing or differs from the registered one) both mean "Fingerprint changed: renew the signing key in Settings"; `ParentAuthUnavailableException` (open) and its subclass `ParentKeyNotRegisteredException` (no registered key) both mean "this device cannot sign", the D-M2-1 fallback.
- **Parent key on API 28–29.** `setUserAuthenticationParameters` arrived in API 30, so the key uses `setUserAuthenticationValidityDurationSeconds(-1)` (per use) and cannot name the allowed authenticators: this code cannot exclude the device credential by policy there. AOSP Keystore on those releases binds per-use keys to the biometric secure user ids only, so in practice a biometric that can mint Keystore auth tokens is required; that is platform behaviour, not verified on an API 28–29 device yet.
- **Parent key needs an enrolled strong biometric.** Keystore refuses to create a per-use biometric key otherwise. Check `availability()` first; `createParentKey()` throws `ParentAuthUnavailableException` without touching Keystore, and a refusal from Keystore itself is mapped to the same exception. Devices without one fall under D-M2-1.
- **Key properties are not attestation.** `DeviceKeyStore.keyProperties()` and `ParentAuthKeyStore.keyProperties()` report what the local OS says through `KeyInfo`. Never base a trust decision about another device on them.
- **AEAD format.** `AesGcmAead` output starts with a version byte (`0x01`). Data encrypted before this change (no version byte) does not decrypt; nothing persisted `Aead` output before M4, so there is no migration.
- **Lockout, clocks and reboots.** `PinLockoutPolicy` never reads the wall clock, so moving it does nothing. A reboot (new boot id) during a running lockout makes the whole lockout due again from the first check after boot, since the served part cannot be known; elapsed realtime earlier than the stored start within one boot id is treated the same way. A lockout that a check already saw expire stays served across a reboot. If `/proc/sys/kernel/random/boot_id` is unreadable, the fallback id does not change on reboot and only the "time ran backwards" rule catches it. A root user can delete the state file; the pepper is what protects the hash in that case.
- **Lockout failures fail closed.** Unreadable state means the cap. If the `pin.lockout` secret can no longer be unwrapped, writes throw; feature/lock must treat any exception from the policy as locked.
- **Argon2 is Android-only.** argon2kt ships JNI libraries only (16 KB page aligned). JVM tests use PBKDF2. `src/androidTest` covers Argon2 and Keystore.

## Tests

- `./gradlew :core:crypto:testDebugUnitTest` runs on the JVM with no Robolectric. It covers ECDSA round trip and tampering plus malformed DER, malformed keys, and a provider that throws at verify time; AES-GCM (round trip, wrong or empty associated data, unknown and relabelled version bytes, tampering, truncation, 10,000 unique nonces); the HKDF RFC 5869 cases 1–3; the X25519 RFC 7748 §5.2 (single and 1/1000-times iterated) and §6.1 vectors plus agreement in both directions, all run against both the JCE and the Tink implementation, Tink/JCE interoperability, and the API-level selection (also under Robolectric on SDK 28 and 35); the chat glue (binding sign/verify, thread-key wrap/unwrap across implementations and every bound field, message and blob encryption including a transplanted ciphertext); the PIN hash formats (`v2` peppered, retired `v1` refused as reset-required, version/algorithm mismatches, another device's pepper, a lost pepper key), length bounds; the parent-signature flow over `FakeParentAuthorizer` (sign once, availability gating, reading never creates a key, invalidation and reset, the exception hierarchy) and `KeystoreParentAuthorizer`'s gating; the biometric status mapping; the lockout schedule, cap, the cap as a timed wait while the parent key is unusable or its health check fails, process death, reboots, time running backwards or far forwards, and unreadable state; the encrypted lockout store and its codec; the wrapped secret store including the `createIfMissing` guard; and the StrongBox-to-TEE fallback logic.
- `src/androidTest/.../AndroidKeystoreInstrumentedTest` needs a device or emulator. It covers Keystore signing, Keystore wrapping with file storage, peppered Argon2id (and refusal of retired M1 hashes), the Keystore HMAC pepper, the encrypted lockout store over real files and the boot id, and the parent key: without an enrolled strong biometric creation must fail with `ParentAuthUnavailableException` and leave no key; with one, the key exists and refuses to sign without a prompt. Each parent-key test runs only in its matching enrolment state (JUnit `assume`). The StrongBox fallback against a real secure element is only exercised on hardware that has one.
