# M2 — Chores, rewards, allowance, savings, parent lock

Scope from `docs/PLAN.md` M2 plus the M2 items of ADR-0004 (including its M2-review amendments) and ADR-0005. Everything here is implemented on branch `m2/chores-rewards-lock` and lands as one PR.

## Domain (pure Kotlin)

New module `core/domain-household` (plugin `sprout.jvm.library`, depends on `core/model`, `core/domain-ledger`, `core/time`). Models live in `core/model`; rules and schedules live here.

- `Chore(id: ChoreId, householdId, kidId, title (≤80), description (≤500, optional), reward: ChoreReward(money: Money?, minutes: Money?) at least one, schedule: ChoreSchedule, createdAt, archived)`.
- `ChoreSchedule`: `Once(dueOn: CalendarDate?)` (an "any time" one-off with no `dueOn` uses its creation date as the occurrence key, so it is paid once; ADR-0005), `Daily(daysOfWeek: Set<DayOfWeek>)`, `Weekly(dayOfWeek)`, `Monthly(dayOfMonth 1..28)`. `ChoreOccurrence(choreId, dueOn: CalendarDate)` is derived, never stored. `ChoreScheduler.occurrences(chore, from, to)` and `nextDue(chore, after)`; pure, tested against a fixed calendar.
- `ChoreSubmission(id, choreId, dueOn, kidId, submittedAt, note (≤200), photoRef: PhotoRef?, status: SUBMITTED | APPROVED | REJECTED, decidedAt, decidedBy: UserId?, rejectionReason (≤200))`. Status precedence for sync: `APPROVED` > `REJECTED` > `SUBMITTED`. An approval produces exactly one `ChoreRewarded` ledger event per reward currency (`choreId` + `dueOn` make the submission id deterministic, so re-approval is idempotent). A rejection is refused once any reward for that occurrence has been paid; a partial approval (one currency paid) is reported and can be finished (ADR-0005).
- `Reward(id: RewardId, householdId, title (≤80), kind: SCREEN_TIME | TREAT | OUTING | OTHER, cost: Money, currency: Currency, minutesGranted: Int? (only for SCREEN_TIME), active, forKids: Set<KidId> (empty = all))`. Purchase → `RewardPurchased` on the fiat MAIN account; a `SCREEN_TIME` reward additionally credits minutes via a `TimeBankCredited` ledger event (new event type, parent-only by default but authorised when it references an accepted `RewardPurchased` eventId; rule: amount == reward.minutesGranted). The purchase and its credit are written together by `appendAllAsKid`, all or nothing; a startup and daily redeem step appends any owed credit (ADR-0005).
- `AllowanceSchedule(kidId, amount: Money, currency, cadence: WEEKLY(dayOfWeek) | MONTHLY(dayOfMonth), startsOn, active)`. `AllowancePlanner.due(schedule, lastPaidOn, today): List<CalendarDate>` (catch-up capped at 8 periods). Each due date → one `AllowancePaid` event with `periodKey` (e.g. `2026-W45` / `2026-11`) so re-planning is idempotent. Periods skipped by the cap are persisted and shown on the parent dashboard.
- `SavingsGoal(id, kidId, title (≤80), target: Money, createdOn, achievedOn?)`. Progress is a projection over the SAVINGS account balance.
- `InterestPolicy(householdId, annualRateBasisPoints 0..2000, accrualDay: dayOfMonth 1..28)`. `InterestPlanner.due(policy, balanceOn, lastAccruedOn, today)` → `InterestAccrued` events using `InterestCalculator`, where `balanceOn(date)` is the SAVINGS balance at the end of that accrual day; catch-up compounds (ADR-0005).
- `PendingParentAction`: a queue of parent-only ledger events that were planned by a scheduler (allowance, interest) but cannot be signed without the parent key. Drained only from a manual **"Sign now"** on the parent dashboard, never automatically at unlock; every prompt names the kid, amount and period (ADR-0004 amendments). Each action is validated against the ledger rules before any prompt; invalid ones are marked `FAILED` and never re-prompt; actions from a changed schedule are cancelled and re-planned; draining is serialised (ADR-0005).

## Ledger envelope v2 (core/domain-ledger)

- `schemaVersion = 2`: adds `parentSignature: String?` (base64, ECDSA P-256 by the parent auth key over `"sprout/ledger-event-parent/v2" || 0x00 || canonical`). Parent-only events (`ChoreRewarded`, `AllowancePaid`, `ManualAdjustment`, `InterestAccrued`, `OverdraftCompensated`, `TimeBankCredited` unless reward-referenced) must carry it when the household policy `requireParentSignature` is true. Parent signatures are on by default when a strong biometric is available: the key is registered at PIN setup (D-M2-8). v1 events remain valid for reading.
- `LedgerRules` gets `ParentSignatureMissing`. In M2 the local writer verifies the parent signature against the key registered in the household policy; a signature by an unregistered key counts as unsigned. Verification of remote events against the household's parent-key registry is M3.
- `LedgerWriter.append` gains an overload for parent-only events that takes a `ParentAuthorization` (an opened `Signature` from a successful `BiometricPrompt` with `CryptoObject`), so the feature layer must prompt before calling.

## Crypto (core/crypto)

- `AndroidKeystoreParentAuthKeyStore`: new alias `sprout.parent.auth.v2`, `setUserAuthenticationParameters(0, AUTH_BIOMETRIC_STRONG)`, `setInvalidatedByBiometricEnrollment(true)`. `ParentSigner.sign(authorization, payload)`. The key is never created lazily: it is created and registered only in a PIN-gated enrolment flow (at PIN setup when a strong biometric is available, or later from Settings with a fresh PIN). Biometric unlock and per-event authorisation are offered only when the local key byte-equals the registered key, and the unlock challenge is verified against the registered key. After a biometric enrolment change invalidates the key, renewal is PIN-gated: fresh PIN under the lockout policy → delete → create → proof prompt → replace the registered key, keeping the original from-lamport (ADR-0004 amendments).
- `ParentAuthAvailability`: STRONG_BIOMETRIC_AVAILABLE | NOT_ENROLLED | NO_HARDWARE. Devices without strong biometrics: events are written without `parentSignature` and the household policy records `parentSignatureRequired = false` with a visible warning in settings (pending decision D-M2-1).
- PIN pepper: `KeystoreHmacPepper` (alias `sprout.pin.pepper.v1`, HMAC-SHA256 key, no user auth); `Argon2idPinHasher` input = HMAC(pin). Format version `v2$argon2id-pepper$...`; unpeppered v1 hashes are not accepted (no M1 build shipped).
- Lockout: `PinLockoutPolicy` persists served time (`SystemClock.elapsedRealtime` + boot id) so a reboot does not reset it; after the cap, a biometric re-auth is required instead of waiting. While the parent key is invalidated or no strong biometric exists, the capped state allows one PIN attempt per hour instead (D-M2-7).

## Data (core/database)

Tables: `chores`, `chore_submissions` (unique `(choreId, dueOn)`), `rewards`, `allowance_schedules`, `savings_goals`, `interest_policy` (single row per household), `pending_parent_actions`, `photos` (local file refs only; bytes encrypted with the household AEAD key placeholder in M2: `Aead` with a per-install key from `SecretStore`; real household key in M4). Photo retention: the camera cache is cleared before each capture and at app start; an encrypted photo is deleted when its submission is decided or its chore or kid is archived (ADR-0005). Schema version 2 with a migration from 1 and a migration test. Repositories: `ChoreRepository`, `RewardRepository`, `AllowanceRepository`, `SavingsGoalRepository`, `InterestPolicyRepository`, `PendingParentActionRepository`. Every document write also writes an outbox row (`kind = DOCUMENT`, `docType`, `docId`, LWW `lamport`).

## Features

- `feature/lock`: first-run PIN setup (6 digits, confirm; registers the parent key when a strong biometric is available), PIN-gated parent-key enrolment and renewal flows, PIN entry with lockout feedback, biometric unlock (`BiometricPrompt`, `BIOMETRIC_STRONG`), `ParentSession` state (locked/unlocked, auto-lock after 2 min in background), `RequireParent { }` composable gate, `FLAG_SECURE` on parent screens, kid-mode exit gate. The parent session is only an app-level gate; money events still need per-event parent authorisation.
- `feature/chores`: parent list/create/edit/archive chores, assign to kid; approvals inbox (submissions with photo preview, approve/reject, each approval prompts the parent authorisation); kid "Today" per tier: Seedling picture cards (max 3, one-tap Done + confetti), Sprout list with due dates, rewards, note + photo; Sapling list plus "propose a chore" (creates a chore in `PROPOSED` state for the parent to accept).
- `feature/wallet` shop: rewards catalogue per tier (Seedling picture tiles with can/can't afford, Sprout prices + "days until", Sapling full catalogue + wishlist; the wishlist is session-only in M2, full persistence M3+), purchase flow (kid-authored `RewardPurchased`; screen-time rewards credit the time bank). **Added in 1.1.2 (2026-11-13, D-REL-59 to 64):** M2 shipped the shop without a parent editor (the catalogue came from a debug-only seed); the Rewards list and reward editor (`RewardListScreen`, `RewardEditorScreen`) now write it through `RewardRepository.upsert`, reached from the dashboard's Rewards button.
- `feature/settings` (minimum): kids & tiers (edit name, birth month, tier override), allowance per kid, interest policy, savings goals per kid, parent PIN change, parent-signature policy status.
- `feature/parent-home`: dashboard cards: pending approvals count, kids' balances, next allowance dates, skipped allowance periods, scheduled payments waiting for "Sign now" (and `FAILED` ones), anomalies; entry to each feature.
- `feature/timebank`: unchanged in M2 except that `TimeBankCredited` feeds it.
- `app`: parent/kid mode switch (parent mode behind the lock; kid mode picks a kid and stays until exit gate), navigation, `WorkManager` periodic planner (daily) that plans allowance and interest into `pending_parent_actions`.

## Screenshot tests

Roborazzi set up via a convention plugin (`sprout.android.screenshot`), one `@Preview`-driven screenshot test per screen × tier × key state for wallet, shop, chores today, lock. Golden images committed under `src/test/screenshots`; CI compares with a small pixel tolerance and uploads diffs on failure; a `Record screenshots` workflow records Linux goldens on demand (D-M2-11, `docs/SCREENSHOT_TESTS.md`).
